# بابی

یک ربات ایجنت همه‌کاره برای تلگرام. بابی فقط چت نمی‌کند: خودش تصمیم می‌گیرد چه ابزاری را صدا بزند، نتیجه را می‌خواند، و بعد جواب می‌دهد.

```
کاربر ──▶ مدل ──▶ [ابزار] ──▶ مدل ──▶ جواب
              ▲                  │
              └──────────────────┘
```

---

## شروع سریع

```bash
bun install
cp .env.example .env
```

سپس در `.env` دو مقدار الزامی را پر کن:

| متغیر | توضیح |
|---|---|
| `TELEGRAM_BOT_TOKEN` | از [@BotFather](https://t.me/BotFather) |
| `OWNER_TELEGRAM_ID` | شناسهٔ عددی خودت، از [@userinfobot](https://t.me/userinfobot) |

```bash
bun run dev
```

ربات با همان تنظیمات بالا کار می‌کند، ولی **بدون مدل واقعی** فقط پاسخ آزمایشی می‌دهد. برای وصل کردن مدل:

1. یک کلید رمزنگاری بساز: `openssl rand -hex 32` و در `BOBI_AI_KEY_MASTER_KEY` بگذار.
2. در تلگرام `/ai` را بفرست.
3. پروایدر اضافه کن (آدرس + کلید API)، مدل اضافه کن، و فعالش کن.

بدون `BOBI_AI_KEY_MASTER_KEY` نوشتن اعتبارنامه **رد می‌شود** — هیچ کلیدی به‌صورت متن ساده ذخیره نمی‌شود.

---

## چه کاری می‌کند

| ابزار | کار |
|---|---|
| `calculator` | جمع، تفریق، ضرب، تقسیم — بدون `eval` |
| `date_time` | تاریخ و ساعت در هر timezone، با پشتیبانی DST |
| `text_utilities` | آمار متن: کاراکتر، کلمه، جمله، خط |
| `unit_converter` | طول، جرم، حجم، دما |
| `fetch_url` | خواندن یک صفحهٔ وب و تبدیلش به متن |
| `web_search` | جستجوی وب (DuckDuckGo بدون کلید، یا Tavily با کلید) |
| `remember` / `recall` / `forget` | حافظهٔ بلندمدت، مجزا برای هر کاربر |
| `remind_at` / `list_reminders` / `cancel_reminder` | یادآور زمان‌دار |
| `mcp_<server>` | هر ابزاری که یک سرور MCP ارائه می‌دهد |

### پیوست‌ها

عکس، پیام صوتی و سند را مستقیم در چت بفرست — بابی خودش برمی‌دارد:

| می‌فرستی | چه می‌شود |
|---|---|
| عکس | بزرگ‌ترین سایز (نه thumbnail) به مدل می‌رود |
| پیام صوتی | به مدل می‌رود (Gemini صدا را مستقیم می‌فهمد) |
| PDF | به‌عنوان سند به مدل می‌رود |

**پیوست در تاریخچه ذخیره نمی‌شود** — فقط یک نشانه (`[۱ پیوست]`). چون base64 در
دیتابیس آن را بی‌مرز بزرگ می‌کند، و مدل نیازی ندارد عکس دیروز را در هر پیام
بعدی دوباره ببیند.

پیوستی که قابل استفاده نباشد **بی‌صدا گم نمی‌شود** — به کاربر گفته می‌شود چرا
(حجم زیاد یا نوع پشتیبانی‌نشده). عکس گم‌شده بدتر از خطاست: مدل با اطمینان دربارهٔ
چیزی حرف می‌زند که هرگز ندیده.

## اتصال ابزارهای بیرونی با MCP

[MCP](https://modelcontextprotocol.io) یک استاندارد باز است: هر سروری که آن را
حرف بزند، ابزارهایش را با خودش می‌آورد. با یک انتگریشن، بابی به کل اکوسیستم
وصل می‌شود — بدون نوشتن تک‌تک ابزارها.

فایل `mcp.json` کنار ربات بساز:

```json
{
  "servers": {
    "files": {
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/dir"],
      "enabled": true
    },
    "remote": {
      "transport": "http",
      "url": "https://mcp.example.com/mcp",
      "token": "…",
      "enabled": false
    }
  }
}
```

هر سرور متصل، یک ابزار `mcp_<name>` می‌شود. مدل نام ابزار واقعی را در فیلد
`tool` و آرگومان‌ها را در `arguments` می‌دهد.

### امنیت MCP

**یک سرور stdio یک دستور پوسته است** که با اختیارات کامل پروسهٔ ربات اجرا
می‌شود. بنابراین:

- فقط **مالک** سرور تعریف می‌کند — نه مدل، نه کاربر عادی.
- هر سرور تا وقتی `"enabled": true` نگوید **اجرا نمی‌شود**. کپی‌کردن یک فایل
  config هیچ‌چیز را اجرا نمی‌کند.
- فیلدهای ناشناخته **رد** می‌شوند، نه نادیده — تا یک غلط تایپی به یک اجرای
  ناخواسته تبدیل نشود.
- مدل فقط ابزاری را می‌تواند صدا بزند که سرور **خودش اعلام کرده باشد**.
- هر خطا در استارتاپ لاگ می‌شود؛ یک سرور خراب بقیه را از کار نمی‌اندازد.

## امنیت

مدل تهدید کامل، مرزهای اعتماد، سطح حمله‌ی هر فاز، و چیزهایی که عمداً نداریم:
**[docs/SECURITY.md](docs/SECURITY.md)** — سند امنیتی یکپارچه‌ی پروژه.

این بخش مهم‌ترین قسمت پروژه است. هر مورد زیر با تست پوشش داده شده.

### ۱. دسترسی کاربر

هر کسی که در چت خصوصی به ربات پیام بدهد ابتدا `pending` می‌شود و **هیچ پاسخی از مدل نمی‌گیرد**. مالک در `/admin → دسترسی کاربران` تأیید یا رد می‌کند. بدون این، هر غریبه‌ای می‌توانست بودجهٔ API تو را خرج کند.

گروه‌ها گردش تأیید جداگانهٔ خودشان را دارند.

### ۲. ابزارها فقط از یک مسیر اجرا می‌شوند

مدل فقط *نام* ابزار را انتخاب می‌کند. مجوز از سرور می‌آید:

- **`ToolActor`** از `ctx.from.id` ساخته می‌شود — هرگز از متن پیام یا خروجی مدل.
- **`ToolExecutor`** تنها مسیر اجراست: بررسی مجوز قبل از بررسی فعال‌بودن، اعتبارسنجی ورودی قبل از اجرا، تایم‌اوت، و سقف هم‌زمانی.
- ابزاری که مدل «اختراع» کند `not_found` می‌گیرد؛ ابزاری که مجوزش را ندارد `not_allowed` — و این به مدل برگردانده می‌شود تا بتواند مسیرش را عوض کند.

### ۳. خروجی ابزار «داده» است، نه «دستور»

هر نتیجه داخل `<tool_result>` پیچیده می‌شود و system prompt صراحتاً می‌گوید محتوای آن دستور نیست. یک صفحهٔ وب مخرب نمی‌تواند به ایجنت بگوید قوانینش را نادیده بگیرد.

### ۴. SSRF

`fetch_url` و جستجو از همان ترانسپورت AI استفاده می‌کنند:

- **`validateTarget`** — scheme، userinfo، و میزبان‌های خصوصی
- **`resolveTarget`** — DNS را resolve می‌کند و **هر** آدرس برگشتی را بررسی می‌کند (دفاع در برابر DNS rebinding)
- **`pinnedFetch`** — سوکت را به آدرس تأییدشده می‌بندد، ریدایرکت را دنبال نمی‌کند، و حجم پاسخ را محدود می‌کند

ریدایرکت‌ها دستی و محدود دنبال می‌شوند، چون هر hop باید دوباره اعتبارسنجی شود — یک URL عمومی که به `169.254.169.254` ریدایرکت کند در غیر این صورت یک SSRF کامل است.

### ۵. بودجه

یک پیام کاربر می‌تواند چندین فراخوانی مدل و ابزار بشود، پس هر چیز سقف دارد:

| سقف | پیش‌فرض | متغیر |
|---|---|---|
| رفت‌وبرگشت مدل | ۶ | `BOBI_AGENT_MAX_ITERATIONS` |
| فراخوانی ابزار در هر پیام | ۱۲ | `BOBI_AGENT_MAX_TOOL_CALLS` |
| زمان کل یک اجرا | ۱۲۰s | `BOBI_AGENT_TOTAL_TIMEOUT_MS` |
| پیام در دقیقه (هر کاربر) | ۲۰ | `BOBI_RATE_LIMIT_PER_MINUTE` |
| ابزار در ساعت (هر کاربر) | ۲۰۰ | `BOBI_RATE_LIMIT_TOOL_CALLS_PER_HOUR` |

وقتی سقفی پر شود، یک فراخوانی نهایی **بدون ابزار** انجام می‌شود تا کاربر با هر چیزی که جمع شده جواب بگیرد، نه اینکه معلق بماند.

### ۶. لاگ

خروجی JSON ساختاریافته در سطح `BOBI_LOG_LEVEL`. یک redactor الگوهای اعتبارنامه (توکن تلگرام، `sk-…`، `tvly-…`، `Bearer …`) و فیلدهای حساس را حذف می‌کند — حتی اگر کدی اشتباهاً سکرتی را پاس بدهد.

## معماری

```
src/
├── index.ts              نقطهٔ شروع: سیم‌کشی همه‌چیز
├── agent/                ← قلب ایجنت
│   ├── loop.ts           حلقهٔ مدل → ابزار → مدل، با بودجه‌ها
│   ├── prompt.ts         ساخت system prompt از فکت‌های سرور
│   └── transcript.ts     واژگان یک اجرا (step، نتیجه، wrap)
├── conversation/
│   ├── engine.ts         یک turn = یک اجرای کامل ایجنت
│   └── summary.ts        خلاصه‌سازی تاریخچهٔ قدیمی
├── ai/                   لایهٔ سرویس‌ها
│   ├── provider.ts       قرارداد neutral (شامل tool calling)
│   ├── gateway.ts        انتخاب پروایدر/مدل + failover
│   ├── {openai_compatible,anthropic,gemini}.ts
│   ├── dns_guard.ts      اعتبارسنجی آدرس
│   ├── pinned_transport.ts  سوکت مقید به آدرس تأییدشده
│   └── secret_store.ts   AES-256-GCM
├── tools/                ابزارها — همه از یک قرارداد
│   ├── types.ts          Tool<TIn, TOut>
│   ├── executor.ts       تنها مسیر اجرا
│   ├── registry.ts       فهرست
│   ├── validate.ts       اعتبارسنجی ورودی
│   └── {calculator,date_time,...}.ts
├── auth/                 هویت و مجوز
├── groups/               تأیید گروه + پنل مالک
├── search/               پروایدرهای جستجو
├── scheduler/            یادآورها
├── storage/              SQLite — تنها جایی که SQL هست
├── core/                 logger، rate limit، usage، deadline
└── config/               خواندن env با پیش‌فرض‌های امن
```

### اصول طراحی

1. **یک قرارداد برای همه‌چیز.** ابزار جدید = یک فایل که `Tool` را پیاده می‌کند.
2. **مرزها صریح‌اند.** موتور grammY نمی‌شناسد؛ ابزارها storage نمی‌شناسند؛ آداپترها فقط wire format می‌دانند.
3. **همه‌چیز قابل تست است.** ساعت تزریق می‌شود، شبکه stub می‌شود، تصمیم‌ها توابع خالص‌اند.
4. **شکست بسته.** خطای storage ≠ تأیید. کلید ناموجود ≠ ادامه با متن ساده.

## افزودن یک ابزار

یک فایل بساز و در `DEFAULT_TOOLS` ثبتش کن. همین.

```ts
// src/tools/word_count.ts
import { ToolError } from "./errors";
import type { Tool, ToolContext } from "./types";

export const wordCountTool: Tool<{ text: string }, { words: number }> = {
  name: "word_count",
  description: "تعداد کلمات یک متن را می‌شمارد.",
  enabled: true,
  permission: { requires: ["tools:word_count"] },
  input: {
    fields: {
      text: { type: "string", required: true, maxLength: 10_000 },
    },
  },
  async run(input, _ctx) {
    const words = input.text.trim().split(/\s+/).filter(Boolean).length;
    if (words === 0) throw new ToolError("invalid_input", "متن خالی است.");
    return { words };
  },
};
```

```ts
// src/tools/service.ts
export const DEFAULT_TOOLS = [
  // ...
  wordCountTool,
];
```

همین کافی است: اعتبارسنجی، مجوز، تایم‌اوت، و تعریف JSON Schema برای مدل **خودکار** اعمال می‌شوند.

**قواعد:**
- در `run` فقط `ToolError` پرتاب کن — نه خطای خام OS یا شبکه.
- ورودی را قبل از استفاده بررسی کن؛ tool body فرض می‌کند ورودی معتبر است، ولی دفاع عمقی ارزان است.
- هیچ‌وقت متن پیام یا سکرت را لاگ نکن.

## وظایف زمان‌بندی‌شده (cron)

علاوه بر یادآورها، بات حالا **وظایف زمان‌بندی‌شده** دارد: عبارت کرون + یک اکشن ساخت‌یافته
(اجرای ابزار، ارسال پیام، یا اجرای ایجنت). فقط مالک می‌تواند وظیفه بسازد/ببیند/حذف کند.

| ابزار | کار |
|---|---|
| `schedule_task` | ساخت وظیفه: `name`، `cron` (مثل `0 9 * * *`)، `timezone`، `action` |
| `list_tasks` | فهرست وظایف به ترتیب نزدیک‌ترین اجرا |
| `cancel_task` | حذف وظیفه |

کرون پنج‌فیلدی استاندارد (`دقیقه ساعت روزِ_ماه ماه روزِ_هفته`) با پشتیبانی از لیست، بازه،
گام (`*/15`)، نام روز/ماه و میان‌برهای `@hourly`/`@daily`/`@weekly`/`@monthly`؛
اعتبارسنجی سخت‌گیرانه و منطقه‌ی زمانی IANA (پیش‌فرض `Asia/Tehran`). وظایف در SQLite
ذخیره و با ری‌استارت برمی‌گردند؛ تصاحب اتمی است (هرگز دو بار اجرا نمی‌شود) و سیاست
عقب‌افتادگی مثل یادآورهاست (تا ۱ ساعت اجرا، بیشتر از آن رد شدن به اسلات بعدی).
جزئیات کامل: [docs/phase-a2-scheduler.md](docs/phase-a2-scheduler.md)

## مهارت‌ها (Skills)

مهارت‌ها فایل‌های مارک‌داون دست‌ساز مالک در پوشه‌ی `./skills` (قابل تنظیم با
`BOBI_SKILLS_DIR`) هستند که رفتارهای تکرارشونده را به ایجنت یاد می‌دهند. هر فایل
frontmatter دارد (`name` و `description` اجباری، `triggers` اختیاری) و بدنه‌ی
مارک‌داون آزاد. در هر پیام، مهارت‌های مرتبط با متن کاربر جستجو و حداکثر ۳ تای آن‌ها
(سقف ۶۰۰۰ کاراکتر) به system prompt تزریق می‌شوند. مهارت‌ها فقط متن راهنمایند:
هیچ مجوزی نمی‌دهند و هیچ کدی اجرا نمی‌کنند؛ پوشه‌ی مهارت‌ها سطح پیکربندی تحت
کنترل مالک است (مثل `.env`) و نباید رمز داخلشان باشد. ابزار `skills` فهرست
مهارت‌ها را نشان می‌دهد. جزئیات: [docs/phase-a3-skills.md](docs/phase-a3-skills.md)

## ماتریس چندرسانه‌ای

هر آداپتر در برابر هر نوع پیوست دقیقاً چه می‌کند (در تست‌ها پین شده):

| پیوست | OpenAI-compatible | Anthropic | Gemini |
|---|---|---|---|
| تصویر | native (`image_url`) | native (بلاک image) | native (`inlineData`) |
| صوت | یادداشت نام‌دار | یادداشت نام‌دار | native (`inlineData`) |
| سند PDF | یادداشت نام‌دار | native (بلاک document) | native (`inlineData`) |
| سند متنی (`text/*`) | **اینلاین در متن** | یادداشت نام‌دار | یادداشت نام‌دار |

هیچ پیوستی بی‌صدا حذف نمی‌شود. سقف‌ها: هر پیوست ۵MB، هر پیام ۸ پیوست، هر پیام
تلگرام ۴ فایل. پیوست‌ها هرگز ذخیره نمی‌شوند (فقط نوبت‌های متنی در تاریخچه ثبت
می‌شود). جزئیات: [docs/phase-a1-multimodal.md](docs/phase-a1-multimodal.md)

## صدا و تصویرسازی

### رونویسی پیام صوتی (B2)

وقتی پروایدر فعال صدای خام را native نمی‌فهمد (امروز همه به‌جز Gemini)، پیام‌های
صوتی تلگرام قبل از رسیدن به موتور رونویسی می‌شوند و با `[متن پیام صوتی]: <متن>`
جایگزین می‌گردند. نیازمند endpoint سازگار با Whisper (`BOBI_TRANSCRIBE_BASE_URL`؛
خالی = غیرفعال). حداکثر ۲ ویس در هر نوبت؛ شکست رونویسی هرگز نوبت را نمی‌کشد.
جزئیات: [docs/phase-b2-transcribe.md](docs/phase-b2-transcribe.md)

### پاسخ صوتی (B3)

دستور `/voice` حالت پاسخ صوتی را برای کاربر روشن/خاموش می‌کند (ذخیره در
`user_prefs`). وقتی روشن است و TTS پیکربندی شده (`BOBI_TTS_BASE_URL`)، جواب‌ها به‌جای
متن به‌صورت ویس فرستاده می‌شوند؛ در صورت شکست TTS، متن + یک یادداشت برمی‌گردد.
جزئیات: [docs/phase-b3-tts.md](docs/phase-b3-tts.md)

### ساخت تصویر (B4)

ابزار `generate_image`: از روی توصیف متنی یک تصویر می‌سازد (`POST
{baseUrl}/images/generations` با `b64_json`). پرامپت ۱ تا ۱۰۰۰ کاراکتر، دقیقاً یک
تصویر در هر فراخوانی، مهلت ۹۰ ثانیه. وقتی `BOBI_IMAGE_BASE_URL` خالی باشد ابزار
اصلاً ثبت نمی‌شود. بایت‌های تصویر از مسیر `extractMedia` به کاربر می‌رسد و هرگز
وارد کانتکست مدل نمی‌شود. جزئیات: [docs/phase-b4-imagegen.md](docs/phase-b4-imagegen.md)

### استخراج متن سند (B5)

سندهای `.docx` و `.xlsx` (و `.pdf` با کتابخانهٔ pure-JS‏ی `pdf-parse`) وقتی
پروایدر سند را native نمی‌فهمد (Anthropic و Gemini می‌فهمند)، به‌صورت محلی و بدون
وابستگی سنگین به متن تبدیل می‌شوند: `[متن سند «نام»]: …`. پارس ZIP دستی با
محافظ‌های zip-bomb (سقف ۲۰۰ ورودی، ۵MB هر ورودی، ۲۰MB مجموع)؛ متن استخراجی سقف
۲۰۰KB. جزئیات: [docs/phase-b5-docextract.md](docs/phase-b5-docextract.md)

## افزونه‌ها و هوک‌ها (E2)

**هوک‌ها**: واکنش‌های اعلانی مالک به رویدادهای چرخه‌حیات — `startup`
(یک‌بار بعد از بالا آمدن، با هویت مالک)، `agent:start` / `agent:end` (هر نوبت، با
هویت همان نوبت)، `tool:end` (بعد از هر اجرای ابزار). تعریف‌ها فایل مارک‌داون با
frontmatter در `<hooksDir>/<event>/` هستند و اکشن فقط از نوع `tool` (با همان
اعتبارسنجی `parseTaskAction` وظایف زمان‌بندی) — بدون اجرای کد از فایل، برخلاف
هرمس که هوک پایتون اجرا می‌کند.

**افزونه‌ها**: پوشه‌ی `plugin.md` (نام/نسخه/توضیح) + زیرپوشه‌های `skills/` و
`hooks/` — واحد ترکیب‌بندی مهارت‌ها و هوک‌های مرتبط، بدون هیچ کد اجرایی.
جزئیات: [docs/phase-e2-plugins-hooks.md](docs/phase-e2-plugins-hooks.md)

### وب‌هوک‌های خروجی

رویدادهای چرخه‌حیات (`agent:start` / `agent:end` / `tool:end`) می‌توانند با
امضای HMAC-SHA256 به URLهای دلخواه مالک POST شوند (سربرگ
`X-Bobi-Signature-256`). پیکربندی با `BOBI_WEBHOOK_URL` و
`BOBI_WEBHOOK_SECRET`؛ URL بدون secret یعنی وب‌هوک خاموش (fail-closed، هرگز
ارسال بدون امضا). بدنه فقط فراداده است (نام ابزار، مدت، شمار توکن) — هرگز متن
پیام یا خروجی ابزار. صف محدود ۱۰۰تایی با retry نمایی. جزئیات:
[docs/phase-webhooks.md](docs/phase-webhooks.md)

## استخر اعتبار و درگاه ابزار

### کلیدهای پشتیبان پروایدر (E3)

هر پروایدر علاوه بر کلید اصلی می‌تواند چند **کلید پشتیبان** داشته باشد. گیت‌وی
در هر درخواست اول کلید اصلی را می‌زند و بعد سراغ پشتیبان‌ها می‌رود؛ اگر کلیدی

کلید بعدی ادامه می‌یابد (بدون کول‌داون)، و خطای پاسخ خراب هیچ‌وقت با کلید
دیگری تکرار نمی‌شود. مدیریت از پنل `/ai` ← «کلید پشتیبان» (فقط مالک، کلید سمت
سرور خوانده و رمزنگاری می‌شود، هرگز نمایش داده نمی‌شود). جزئیات:
[docs/phase-e3-pools.md](docs/phase-e3-pools.md)

### تول‌ست‌ها و جستجوی ابزار (E4)

دیده می‌شود. `setActiveToolsets()` فیلتر ارگونومیک پرامپت است (پیش‌فرض: همه)
و مرز امنیتی واقعی همان مجوزهای `ToolActor` می‌ماند. ابزار `tool_search` به

## بسته‌های زبانی (D5)

رشته‌های کاربر-رو از بسته‌های زبانی می‌آیند (`src/i18n/`). **فارسی پیش‌فرض
است** و بسته‌ی فارسی بایت‌به‌بایت همان متن قبلی است — کاربران فعلی هیچ تغییری
نمی‌بینند؛ `en` دومین بسته است. ترجمه‌ی گمشده هیچ‌وقت به پاسخ خالی تبدیل
نمی‌شود (برگشت به فارسی، بعد به خود کلید). زبان هر فرستنده از `user_prefs`
با کلید `lang` خوانده می‌شود؛ فقط رشته‌ی دقیق `en` انگلیسی را انتخاب می‌کند و
هر چیز دیگر (گمشده/خالی/نامعتبر) به فارسی برمی‌گردد. متن‌های روبه‌مدل (توصیف
ابزارها) عمداً ترجمه نشده‌اند چون مدل به فارسی کار می‌کند. جزئیات:
[docs/phase-d5-i18n.md](docs/phase-d5-i18n.md)

### قرارداد دوزبانه (بیلینگوال)

ربات باید کاملاً دوزبانه باشد: فارسی و انگلیسی. دو خانه برای رشته‌ها داریم
(تصمیم coordinator) و دوزبانه‌بودن هر دو با **تست** تضمین می‌شود، نه با محل فایل:

1. **پک‌های مرکزی** (`src/i18n/fa.ts` و `src/i18n/en.ts`) — رشته‌های مشترک
   کل ربات (منوها، `/help`، دستورهای داخلی، گیت‌ها، `/lang`). مصرف با
   `t(key, lang, vars)`. فارسی مرجع (ground truth) است و انگلیسی آینه‌ی آن.
2. **جدول‌های محلی ماژول** (`src/**/*_strings.ts`) — رشته‌های مختص یک ماژول
   دستوری (مثلاً `cmd_session_strings.ts`). مصرف با `tr(lang, key, vars)` همان
   ماژول. هر جدول باید هر دو زبان را کامل داشته باشد.

تست `tests/i18n_parity.test.ts` نگهبان این قرارداد است: برابری کلیدهای fa/en
در هر دو جهت، خالی‌نبودن هیچ ترجمه‌ای، یکسان‌بودن مجموعه‌ی `{placeholder}`ها
در هر دو زبان برای هر کلید، و پوشش همه‌ی صدازننده‌های `t("...")`. جدول‌های
محلی با glob پیدا می‌شوند — جدولی که بعداً اضافه شود خودکار زیر تست می‌رود.

### چطور یک رشته‌ی جدید اضافه کنی

- رشته‌ی مشترک: کلید جدید در **هر دو** فایل `fa.ts` و `en.ts` (کلیدها نقطه‌ای،
  مثل `menu.label.chat`). فارسی را تنگ و خودمونی بنویس؛ انگلیسی باید مثل متن
  یک نیتیو بخواند، نه ترجمه‌ی کلمه‌به‌کلمه. ایموجی و قالب‌بندی در هر دو زبان
  یکی باشد.
- رشته‌ی مختص ماژول: در `*_strings.ts` همان ماژول، هر دو زبان را کامل بگذار
  (یکی از دو شکل پشتیبانی‌شده: دو جدول `FA`/`EN` یا رکورد `{ fa, en }` برای
  هر کلید) و مطمئن شو ماژول `tr(lang, key, vars)` را export می‌کند.
- `{placeholder}`ها فقط از مقادیر سمت‌سرور پر می‌شوند (نام دستور، شمارنده،
  برچسبِ مالک) — **متن خام کاربر هرگز داخل قالب تزریق نمی‌شود**.
- بعد از اضافه‌کردن، `bun test tests/i18n_parity.test.ts` را اجرا کن؛ اگر
  جایی جا انداخته باشی همین‌جا می‌گیری‌اش.

### جریان `/lang`

`/lang` یک انتخاب‌گر دوزبانه نشان می‌دهد (دکمه‌های فارسی / English)؛ با زدن
دکمه، انتخاب در `user_prefs` با کلید `lang` ذخیره و پیام تأیید همان‌لحظه به
**زبان جدید** فرستاده می‌شود. `resolveLang` فقط رشته‌ی دقیق `en` را قبول
می‌کند — هر مقدار خراب یا جعلی (از callback دست‌کاری‌شده یا pref آلوده) بی‌صدا
به فارسی برمی‌گردد، پس پک ناموجود هیچ‌وقت انتخاب نمی‌شود. همه‌ی سطوح مرکزی
(منوی اصلی، پاسخ دکمه‌ها، `/help`، خطاهای گیت، حالت‌های خالی) با همین زبان
رندر می‌شوند؛ تست `tests/lang_switch.test.ts` کل سفر «تغییر زبان و برگشت»
را end-to-end پوشش می‌دهد. توضیحات منوی تلگرام (`setMyCommands`) هم در دو
نسخه ثبت می‌شود: فارسی پیش‌فرض و نسخه‌ی `language_code: "en"`.

## دستورها و شخصیت (G1)

| دستور | کار |
|---|---|
| `/help` | فهرست دستورهای مجاز برای فرستنده (دستورهای مالک‌محور برای غیرمالک پنهان) |
| `/reset` | پاک کردن تاریخچه‌ی همین گفتگو |
| `/personality` | نمایش/تغییر شخصیت (`default`، `concise`، `playful`) |
| `/compress` | فشرده‌سازی دستی خلاصه‌ی گفتگوی فعلی |

| `/lang` | تغییر زبان رابط (فارسی/English) — انتخاب per-user |

### منوی اصلی و `/help`

`/start` یک صفحه‌ی آنبوردینگ واقعی نشان می‌دهد (معرفی قابلیت‌ها در چهار گروه
گفت‌وگو/نشست‌ها/اتوماسیون/مدیریت + سه پیشنهاد برای شروع) با منوی اصلی شش‌بخشی:
گفت‌وگو، ابزارها، فرمان‌ها، تنظیمات، درباره‌ی بابی، راهنما. دکمه‌ها پیام را
**درجا ویرایش** می‌کنند (پاسخ‌های پشت‌سرهم تلنبار نمی‌شود) و هر صفحه یک دکمه‌ی
«بازگشت» دارد — بن‌بست نیست. `/help` به‌جای دیوار ۶۳خطی، در چهار بخش (عمومی،
نشست، اتوماسیون، مالک) با مثال کاربرد یک‌خطی هر دستور (`/history 20`) فهرست
می‌شود؛ دستورهای مالک‌محور برای غیرمالک پنهان‌اند.

منوی تلگرام (`setMyCommands`) در هر دو زبان ثبت می‌شود: اسکوپ عمومی ۸ دستور
اصلی داخلی (`start` تا `compress`) + ۲۸ دستور عمومی هرمس، و اسکوپ مالک همه به‌علاوه‌ی
`admin` و `ai` و دستورهای مالک‌محور. ترتیب عمدی است: اول دستورهای اصلی، بعد
گروه‌های هرمس (نشست ← سیستمی ← اتوماسیون). رشته‌های این سطوح در جدول محلی
`src/bot/menu_strings.ts` است (فارسی مرجع، انگلیسی آینه) و تست جفت‌بودن آن را
`tests/i18n_parity.test.ts` نگه می‌دارد.

۵۳ دستور از رجیستری دستوری هرمس (`hermes_cli/commands.py`) روی بات پیاده شده —

## محدودیت‌ها

صادقانه:

- **آداپترها روی endpoint واقعی تست نشده‌اند.** پارس با fixture تست می‌شود، ولی صحت زنده نیاز به کلید واقعی دارد.
- **پارسر DuckDuckGo به HTML عمومی تکیه دارد.** ممکن است یک روز بشکند؛ در آن صورت تست با پیام واضح شکست می‌خورد، نه خرابی خاموش.
- **یادآورها در پروسه اجرا می‌شوند.** اگر ربات خاموش باشد یادآور نمی‌رسد — ولی در استارتاپ بعدی یادآورهای عقب‌افتاده (تا یک ساعت) می‌رسند.
- **هزینهٔ نمایش‌داده‌شده تخمینی است.** جدول قیمت نشانگر است، نه صورت‌حساب.
- **rate limit در حافظه است.** ری‌استارت آن را پاک می‌کند.
