# ورکر پس‌زمینهٔ بنچ‌مارک زنده (Phase-4 Item 2)

> وضعیت: پیاده‌سازی کامل در `src/bench/worker.ts` (+ `worker_strings.ts`)،
> توسعهٔ `src/bench/tool.ts` (مسیر `background`)، توسعهٔ سطح `/bench`
> (`cmd_phase3_bench.ts` + `cmd_phase3_bench_strings.ts`) و سیم‌کشی در
> `src/index.ts`. جدول‌های `bench_runs` / `bench_run_scores` / `bench_alerts`
> بدون تغییر ساختار استفاده می‌شوند (فقط مقادیر `status` گسترده‌تر شد).

## مسئله

فاز ۳ زمان‌بندی بنچ‌مارک را اضافه کرد (`run_bench` + `/bench schedule` +
هشدار افت کیفیت)، اما اجرای **زنده** روی زمان‌بندی هیچ‌وقت واقعی نشد:

- هر اکشن زمان‌بند (TaskScheduler) بودجهٔ حدوداً **۳۰ ثانیه** دارد.
- یک اجرای زندهٔ کامل (۲۴ تسک با فراخوانی واقعی provider) **چند دقیقه**
  طول می‌کشد.
- نتیجه: اکشن `run_bench --live` روی زمان‌بندی همیشه timeout می‌خورد و
  وظیفه «failed» می‌شد؛ بنچ‌مارک زندهٔ زمان‌بندی‌شده عملاً وجود نداشت.

## راه‌حل: صف سبک + ورکر دیمون

کار سنگین از مسیر اکشن زمان‌بند **خارج** شد:

```
تیک زمان‌بند → run_bench {mode:"live", background:true}
    → BenchJobQueue.enqueue (چند میلی‌ثانیه، بدون هیچ فراخوانی LLM)
    → خروجی «queued» → وظیفهٔ زمان‌بندی «ok» می‌شود
ورکر دیمون (pump هر ۲ ثانیه، unref)
    → برداشتن نوبت بعدی → ساخت استک بنچ (همان سازنده‌های CLI)
    → اجرای کامل سوئیت با provider واقعی
    → ثبت در bench_runs (+ per-task scores)
    → مسیر هشدار افت کیفیت موجود (baseline.ts)
    → پیام جمع‌بندی به دایرکت مالک
```

اکشن زمان‌بند حالا خیلی زیر ۳۰ ثانیه تمام می‌شود و هیچ فراخوانی مدلی
داخلش نیست؛ همهٔ هزینه و زمان در ورکر است.

## اجزا

- **`src/bench/worker.ts`**
  - `BenchJobQueue`: دقیقاً یک اجرای فعال + حداکثر ۲ نوبت در صف. بیشتر
    از آن با دلیل `queue_full` **رد** می‌شود (نه گم، نه خراب) و دلیلش لاگ
    می‌شود.
  - `BenchWorker`: حلقهٔ pump، اجرای یک جاب، timeout هر اجرا (پیش‌فرض
    ۲۰ دقیقه، cooperative: بین تسک‌ها چک می‌شود؛ هر turn جدا توسط
    timeout خودِ انجین محدود است)، لغو توسط مالک.
  - قفل سراسری فرایند (`tryAcquireBenchRunLock`): مسیر سنکرون
    `run_bench` هم همین قفل را می‌گیرد. اگر ورکر مشغول باشد، اجرای دستی
    **با صدای بلند** خطای `overloaded` می‌دهد — چون state شبیه‌سازی وب
    در `bench/run.ts` ماژول-global است و دو سوئیت هم‌زمان به هم دادهٔ
    اشتباه می‌دادند. خطای بلند بهتر از امتیاز ساکتِ اشتباه است.
- **`src/bench/tool.ts`**: ورودی جدید `background?: boolean` و
  `source?: "schedule" | "manual"`.
  - `background: true` → فقط enqueue، خروجی `status: "queued"`.
  - `background: false` → رفتار سنکرون قبلی، بدون تغییر.
  - پیش‌فرض (undefined): اگر `mode:"live"` باشد **و** ورکر وصل باشد،
    خودکار enqueue می‌شود — پس اکشن‌های زمان‌بندی قدیمیِ `{mode:"live"}`
    هم دیگر بودجهٔ زمان‌بند را نمی‌سوزانند. بدون ورکر وصل، رفتار قبلی
    می‌ماند (تست‌ها و بیلدهای بدون ورکر عوض نشدند).
- **`src/bench/history.ts`**: `recordRun` حالا `status` های
  `"failed"` و `"cancelled"` هم می‌پذیرد. خط‌مبنا فقط `status='ok'`
  را می‌خواند، پس اجراهای ناموفق خط‌مبنا را آلوده نمی‌کنند.
- **`/bench`** (مالک، دوزبانه):
  - `/bench run [--live] [--bg]` — `--bg` اجرا را به ورکر می‌سپارد.
  - `/bench schedule <cron|off> [--live]` — زمان‌بندی زنده حالا اکشن
    `{mode:"live", background:true, source:"schedule"}` می‌سازد.
  - `/bench status` — بخش جدید وضعیت ورکر: بیکار / در حال اجرا / تعداد
    در صف.
  - `/bench cancel` — خالی کردن صف و لغو اجرای فعال (cooperative: بعد
    از تسک جاری می‌ایستد).
- **`src/index.ts`**: ساخت `BenchWorker` (تاریخچهٔ مشترک، همان کانال
  `notifyOwner`، زبان از `/lang` مالک)، `benchWorker.start()` کنار بقیهٔ
  زمان‌بندها، `stop()` در خاموشی، و اضافه شدن وضعیت ورکر به health detail.

## حالت‌های خرابی

| حالت | رفتار |
|---|---|
| timeout اجرا (۲۰ دقیقه) | ثبت با `status:"failed"` + شمارش خطای پیاپی |
| خطای provider وسط اجرا | ثبت `failed`؛ پیام جزئی (حداکثر ۳۰۰ کاراکتر، بدون secret) |
| کرش داخل `runJob` | گرفته می‌شود، لاگ می‌شود، قفل آزاد می‌شود؛ pump هرگز نمی‌میرد |
| live بدون provider پیکربندی‌شده | «رد شدن با صدای بلند» (همان قانون refuse-to-fake)؛ پیام مالک با cooldown ۲۴ ساعته؛ رکوردی ثبت نمی‌شود؛ شمارندهٔ خطا زیاد نمی‌شود |
| لغو توسط مالک (`/bench cancel`) | ثبت با `status:"cancelled"`؛ پیام/هشدار جدا ندارد (پاسخ خود دستور کافی است) |
| صف پر | اکشن `skipped` برمی‌گرداند (وظیفهٔ زمان‌بندی «ok» می‌ماند) + لاگ دلیل |
| قفل در دست ورکر و اجرای دستی هم‌زمان | خطای بلند `overloaded`، بدون corruption |

## سیاست هشدار (بدون اسپم)

- **افت کیفیت**: همان مسیر فاز ۳ — مقایسه با میانگین ۵ اجرای اخیر
  (حداقل ۳ اجرا)، آستانهٔ ۵ واحد، cooldown ۲۴ ساعته برای هر کلید
  `regression:<mode>:<model>`.
- **خطاهای پیاپی**: بعد از **۳** اجرای ناموفقِ پشت سر هم، **یک** هشدار
  فشرده به مالک؛ بعدش حداکثر هر ۲۴ ساعت یک‌بار. اجرای موفق شمارنده را
  صفر می‌کند. لغو و skip شمارنده را دست نمی‌زنند.
- **اجرای دستی پس‌زمینه** (`--bg`): چون مالک مستقیماً خواسته، خرابیِ
  تکی هم با یک پیام کوتاه به او اعلام می‌شود. اجراهای زمان‌بندی‌شده
  فقط از مسیر «خطاهای پیاپی» خبر می‌دهند.
- **اتمام موفق**: یک پیام جمع‌بندی (میانگین، موفق/کل، شناسهٔ ثبت).

## بررسی سطح حمله (attack-surface review)

ورکر روی زمان‌بند فراخوانی خروجی به provider می‌زند — کنترل هزینه:

1. **حداکثر یک اجرای هم‌زمان** (قفل فرایند) + صف محدود (۲ نوبت).
2. **timeout هر اجرا** (پیش‌فرض ۲۰ دقیقه)؛ هر turn هم سقف خودِ انجین را
   دارد (۳۰ ثانیه آفلاین / ۱۲۰ ثانیه زنده).
3. **فقط مالک**: enqueue فقط از ابزارِ `ownerOnly` + چک `isOwner`
   سمت سرور می‌آید؛ ساخت زمان‌بندی، `/bench status` و `/bench cancel`
   هم فقط مالک. کاربر عادی نه می‌تواند صف بسازد، نه ببیند، نه لغو کند.
4. **سطح شبکهٔ جدیدی نیست**: فقط همان providerِ پیکربندی‌شدهٔ مالک
   (مثل `bun bench/run.ts --live`)؛ دسترسی وب همچنان mock است؛ state
   هر اجرا در `:memory:` جدا و دورریختنی است.
5. **secret هرگز لاگ نمی‌شود**: پیام خطاها کوتاه و بدون payload
   provider هستند؛ کلیدها فقط از secret store خوانده می‌شوند.
6. پیش‌فرض همه‌چیز **خاموش** است: بدون `/bench schedule` هیچ اجرایی
   روی زمان‌بند نمی‌رود.
