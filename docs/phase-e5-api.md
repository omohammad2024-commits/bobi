# فاز E5 — سرور HTTP حداقلی (health + trigger)

یک سرور HTTP کوچک با `Bun.serve` در `src/http/server.ts` که دو endpoint دارد:

| مسیر | متد | احراز هویت | پاسخ |
|---|---|---|---|
| `/health` | GET | ندارد | `{ ok: true, version }` |
| `/api/v1/turn` | POST | توکن Bearer (`BOBI_API_TOKEN`) | `{ reply }` |

## راه‌اندازی

| متغیر محیطی | نقش | پیش‌فرض |
|---|---|---|
| `BOBI_API_TOKEN` | توکن مشترک احراز هویت | خالی = **سرور اصلاً استارت نمی‌شود**؛ بات دقیقاً مثل قبل بالا می‌آید (هیچ پورتی باز نمی‌شود) |
| `BOBI_API_BIND` | آدرس بایند | `127.0.0.1` |
| `BOBI_API_PORT` | پورت | `8472` |

**نکتهٔ additivity:** اگر `BOBI_API_TOKEN` تنظیم نباشد، هیچ تغییری در رفتار بات نیست. استارت سرور هم در `try/catch` پیچیده شده تا خرابی API هرگز بات را از پا نیندازد، و در خاموش‌شدن منظم (`SIGINT`/`SIGTERM`) سرور هم بسته می‌شود.

## قرارداد `/api/v1/turn`

- هدر: `Authorization: Bearer <token>`
- بدنه (JSON): `{ userId, conversationId, text }`
- اعتبارسنجی: هر سه فیلد رشته‌ای، غیرخالی؛ `text` حداکثر **۴۰۰۰ کاراکتر**؛ کل بدنه حداکثر **۶۴ کیلوبایت**.
- یک دور کامل `ConversationEngine.respond` اجرا می‌شود و پاسخ مدل در `{ reply }` برمی‌گردد (چانک‌های تلگرامی با `\n\n` به هم چسبیده‌اند).
- کدهای خطا: `400` ورودی نامعتبر، `401` توکن نامعتبر، `405` متد نامجاز، `413` بدنهٔ بیش‌ازحد بزرگ، `429` رد شدن از سقف نرخ، `503` توکن پیکربندی نشده، `500` خطای داخلی.
- همهٔ پیام‌های خطا فارسی و کلی‌اند؛ جزئیات داخلی (استک، پیکربندی، دلیل رد احراز هویت) هرگز لو نمی‌رود.

## مدل امنیتی / سطح حمله

1. **توکن، تنها احراز هویت است.** `BOBI_API_TOKEN` باید بلند و تصادفی باشد (مثل خروجی `openssl rand -hex 32`) و **هرگز** لاگ نشود، در پاسخ‌ها برنگردد و در پیام خطا تکرار نشود. مقایسه با `crypto.timingSafeEqual` روی هش SHA-256 هر دو طرف انجام می‌شود تا زمان‌بندی پاسخ، درستی حدس را لو ندهد؛ هدر جاافتاده و توکن اشتباه یک 401 یکسان می‌گیرند (عدم تمایز، no user enumeration).
2. **ترن همیشه با اکتورِ مالکِ ساخته‌شده در سمت سرور اجرا می‌شود** (همان الگوی `actorForOwner` هارتبیت در `src/index.ts`؛ ساخته‌شده از `ownerId` اعتبارسنجی‌شده). چرا؟ کانال HTTP هویت تلگرام را دور می‌زند: اگر `userId` بدنه به اکتور ارتقا پیدا می‌کرد، هر دارندهٔ توکن می‌توانست با هویت هر کاربری عمل کند. پس `userId`/`conversationId` بدنه فقط «وضعیت» را انتخاب می‌کنند، نه «اختیار» را.
3. **بایند پیش‌فرض لوکال‌هاست است** (`127.0.0.1`). بایند به `0.0.0.0` یعنی endpointای که فقط با یک توکن محافظت می‌شود روی شبکه باز است؛ فقط پشت reverse proxy مطمئن انجام شود.
4. **سقف اندازهٔ درخواست:** بدنه بالای ۶۴KB رد می‌شود (قبل از `JSON.parse`) و `text` بالای ۴۰۰۰ کاراکتر رد می‌شود — حلقهٔ عامل نباید ورودی نامحدود بگیرد.
5. **محدودیت نرخ سادهٔ درون‌حافظه‌ای:** ۳۰ درخواست در دقیقه برای هر IP، **قبل** از احراز هویت روی `/api/v1/turn` اعمال می‌شود تا هم flood و هم brute-force توکن کند شود. (درون‌حافظه‌ای است؛ با ری‌استارت ریست می‌شود و بین نمونه‌ها به اشتراک گذاشته نمی‌شود — برای تهدیدمدل فعلی کافی است.)
6. `/health` عمداً بدون احراز هویت است: فقط «زنده‌ام» می‌گوید (همان اصل `src/core/health.ts`) و هیچ چیز دیگری لو نمی‌دهد؛ متدهای غیر GET با 405 رد می‌شوند.

## تست‌پذیری

`createApiServer(deps, { listen: false })` هندلر `fetch` را بدون بایند کردن پورت واقعی برمی‌گرداند؛ تست‌ها (`tests/http_api.test.ts`) مستقیم با آبجکت `Request` صدایش می‌زنند. موتور از طریق `engineFactory` تزریق می‌شود تا تست با `FakeProvider` یک دور واقعی اجرا کند و ثابت شود ترن با اکتور مالکِ سمت سرور اجرا می‌شود، نه با هویت بدنهٔ درخواست.

## سیم‌کشی در `src/index.ts`

بعد از بالا آمدن بات (بخش health): اگر `BOBI_API_TOKEN` ست باشد، سرور با `storage` و موتور اصلیِ از قبل ساخته‌شده (`engineFactory: () => engine`) و `actorForOwner: () => actorForUser(ownerIdStr)` استارت می‌شود؛ آدرس بایند لاگ می‌شود (توکن هرگز). پورت نامعتبر به پیش‌فرض 8472 برمی‌گردد.
