# داشبورد مالک بابی (Owner Web Dashboard)

> آیتم ۳ از فاز ۳. داشبورد وبِ فقط-مالک که روی همان HTTP سرور موجود (`src/http/server.ts`) سوار می‌شود؛ هیچ listener دومی باز نمی‌کند.

## راه‌اندازی

دو متغیر محیطی:

| متغیر | نقش |
|---|---|
| `BOBI_API_TOKEN` | توکن مشترک احراز هویت (همانی که `/api/v1/turn` را گیت می‌کند). بدون آن داشبورد اصلاً بالا نمی‌آید. |
| `BOBI_DASHBOARD=1` | فلگ فعال‌سازی. پیش‌فرض **خاموش** است؛ مقادیر `1` / `true` / `yes` / `on` (غیرحساس به حروف) روشنش می‌کنند. |

متغیرهای دیگری که داشبورد مستقیم می‌خواند (آینهٔ `src/config/config.ts` چون `src/index.ts` دست نخورده):

| متغیر | نقش |
|---|---|
| `OWNER_TELEGRAM_ID` | اسکوپ حافظه + نگهبان «خودت را بن نکن» + مالکِ زمان‌بندها. در عمل همیشه ست است (بات بدون آن بالا نمی‌آید). |
| `AI_KEY_MASTER_KEY` | کلید مستر برای `ProviderSecretStore` (فقط برای ساخت سرویس؛ هیچ کلیدی به مرورگر نمی‌رود). |
| `BOBI_BENCH_RESULTS_DIR` | (اختیاری، بیشتر برای تست) مسیر `bench/results`. |
| `DB_PATH` | (فاز ۴) مسیر فایل SQLite برای خواندن تاریخچهٔ بنچ‌مارک؛ پیش‌فرض `data/bobi.db`، دقیقاً مثل `src/config/config.ts`. داشبورد مثل `src/index.ts` یک اتصال دوم به همان فایل باز می‌کند (فقط خواندنیِ تاریخچه). |

بعد از ست کردن، همان پورت API (پیش‌فرض `127.0.0.1:8472`) مسیر `/dashboard` را هم سرو می‌کند.

## نمودار روند بنچ‌مارک (فاز ۴)

بالای صفحهٔ بنچ‌مارک‌ها یک نمودار خطی SVG نمایش داده می‌شود: سری میانگین کلی امتیازها در طول زمان، و با انتخاب یک تسک از سلکتور، سری امتیاز همان تسک هم روی همان نمودار می‌آید. داده از جدول‌های `bench_runs` / `bench_run_scores` خوانده می‌شود (همان داده‌ای که `/bench trend` به‌صورت متنی چاپ می‌کند).

- **بدون هیچ کتابخانهٔ خارجی**: نمودار با یک رندرر دست‌ساز (`buildLineChartSvg` در `src/http/dashboard_render.ts`) تولید می‌شود — بدون CDN، بدون JS خارجی (حریم خصوصی + کارکرد آفلاین). مثل `escapeHtml`/`renderSafeMarkdown`، تابع خالص و بدون ایمپورت است و با `.toString()` عیناً در مرورگر جاسازی می‌شود؛ همان کدی که تست واحد دارد در کلاینت اجرا می‌شود.
- **راست‌به‌چپ**: در حالت فارسی محور زمان از راست به چپ است (قدیمی سمت راست) و برچسب‌ها فارسی‌اند.
- **XSS**: همهٔ لیبل‌ها و تیک‌ها (از جمله `titleFa` تسک‌ها) قبل از رفتن به SVG از `escapeHtml` می‌گذرد و مختصات عددی اعتبارسنجی/محدود می‌شوند.

## مدیریت زمان‌بندها از وب (فاز ۴) + کرون سفارشی و ویرایش خلاصه (فاز ۵)

صفحهٔ «زمان‌بندها» دو زمان‌بندی‌ای را که امروز فقط از تلگرام مدیریت می‌شدند، به وب می‌آورد:

| زمان‌بند | معادل تلگرام | کنترل‌های وب |
|---|---|---|
| بنچ‌مارک زمان‌بندی‌شده | `/bench schedule <cron\|off>` | روشن/خاموش + دوره از فهرست سفید (`روزانه/هفتگی/ماهانه` = ساعت ۳ بامداد تهران) + **کرون سفارشی** + حالت (`آفلاین/زنده`) |
| خلاصهٔ صبحگاهی | `/blueprint run morning_digest` | روشن/خاموش + ساعت ارسال (تهران، `HH:MM`) + **کرون سفارشی** + **پرامپت و مقصد** |

نکته‌های پیاده‌سازی (فاز ۴ + ۵):

- **فهرست سفید کرون + کرون سفارشی اعتبارسنجی‌شده**: وب همچنان سه دورهٔ ازپیش‌تأییدشده را دارد؛ فاز ۵ یک فیلد «کرون سفارشی» هم اضافه کرده که **اول** `parseCron` را پاس می‌کند و **دوم** کف فاصلهٔ اجرا را نگه می‌دارد: بنچ‌مارک حداقل هر ۱ ساعت، خلاصه حداقل هر ۱۵ دقیقه (سه اسلات آینده در `Asia/Tehran` محاسبه می‌شود؛ کرونِ `* * * * *` رد می‌شود). کرونِ سفارشیِ خالی یعنی «از انتخاب بالا استفاده کن». کرون دلخواهی که از تلگرام ست شده باشد «سفارشی» نمایش داده می‌شود و با انتخاب از وب جایگزین می‌شود.
- **خاموش ≠ حذف**: برخلاف `schedule off` تلگرام که ردیف را پاک می‌کند، دکمهٔ خاموشِ وب فقط فلگ `enabled` را می‌بندد تا تاریخچه و تنظیمات بماند؛ روشن‌کردنِ دوباره همان ردیف را با `nextRunAtMs` تازه فعال می‌کند.
- **خلاصهٔ صبحگاهی — مالکیت `/blueprint`**: به‌روزرسانی ساعت/کرون هرگز اکشن را دست نمی‌زند — `chatId` و پرامپتی که مالک (با `/blueprint`) ست کرده حفظ می‌شود. فاز ۵ **پرامپت** و **مقصد** را هم از وب قابل ویرایش کرده (`/digest/config|prompt|destination`)، اما **از همان ردیف و همان استور** (`storage.updateTask` — همان‌جایی که `/blueprint` می‌نویسد)؛ UI صراحتاً نشان می‌دهد ردیف متعلق به `/blueprint` است و اجرای دوبارهٔ `/blueprint run morning_digest` پرامپت را به پیش‌فرض برمی‌گرداند. ویرایش فقط وقتی مجاز است که اکشن ردیف واقعاً `agent` باشد (ردیفِ دست‌کاری‌شده به شکل دیگر → ۴۰۰، بدون دست‌زدن). پرامپت حداکثر ۴۰۰۰ کاراکتر (همان سقف `parseTaskAction`) و با همان ولیدیتور زمان‌بند اعتبارسنجی می‌شود؛ مقصد فقط شناسهٔ چت عددی (`/^-?\d{1,20}$/`).
- **خلاصه‌های گروه (تب «گروه‌ها»)**: معادل وبِ `/gassistant digest on|off|time HH:MM` — فهرست همهٔ گروه‌های دارای پیکربندی دستیار (از کلیدهای `gacfg:`، فقط مالک) با وضعیت خلاصه و تسکِ هر گروه، و مدیریت روشن/خاموش/ساعت. معناشناسی دقیقاً همان هندلر تلگرام است: تسک **قبل** از روشن‌شدنِ کانفیگ ساخته می‌شود (زمان‌بندیِ ناموفق → کانفیگ دروغ نمی‌گوید)، خلاصه بدون حالت دستیار روشن نمی‌شود (`need_mode`)، و تحویل همیشه به دایرکت مالک است — فقط گروهی که تاریخچه‌اش خوانده می‌شود قابل انتخاب است. ردیف تسک با همان هلپرهای فاز ۴ (`ensureGroupDigestTask`/`cancelGroupDigestTask`) مدیریت می‌شود.
- **اعتبارسنجی سمت سرور**: `enabled` باید بولی باشد؛ `cadence` دقیقاً یکی از سه کلید فهرست سفید (یا `cron` سفارشیِ معتبر)؛ `cron` سفارشی باید پارس شود و کف فاصله را رعایت کند؛ `mode` فقط `offline`/`live`؛ `time` دقیقاً `HH:MM` صفرپدشده؛ پرامپت ۱ تا ۴۰۰۰ کاراکتر؛ `chatId` عددی. هر مقدار دیگری → `400` با پیام فارسی ژنریک.
- **لاگ حسابرسی**: هر تغییر (موفق، ردشده، خطا) با `storage.appendAudit` ثبت می‌شود (`operation: dashboard.scheduler.bench|digest`، `dashboard.digest.config`، `dashboard.group_digest`، `actorId` = شناسهٔ مالک)؛ جزئیات فقط کلیدهای بی‌خطر است (دوره، حالت، ساعت، شناسهٔ ردیف، طول پرامپت — **متن پرامپت هرگز لاگ نمی‌شود**). خرابی لاگ هرگز خودِ تغییر را بلاک نمی‌کند.
- هر دو زمان‌بند در `Asia/Tehran` اجرا می‌شوند؛ بعد از هر تغییر، `nextRunAtMs` از نو محاسبه می‌شود تا سری دچار drift نشود.

## پخش زندهٔ پیشرفت بنچ‌مارک (فاز ۵)

بالای تب «بنچ‌مارک‌ها» یک کارت «اجرای زنده» هست که از مسیر SSE بالا تغذیه
می‌شود: وقتی ورکر در حال اجراست نوار پیشرفت (تسک‌های تمام‌شده از کل)، عنوان
تسک جاری و ثانیه‌شمار سپری‌شده را نشان می‌دهد؛ وقتی بیکار است «اجرای فعالی
نیست» و تعداد در صف را. بعد از پایان یک اجرا، نتیجه («تمام شد: موفق/ناموفق…»
+ شناسهٔ ثبت) می‌ماند تا اجرای بعدی شروع شود.

نکته‌های پیاده‌سازی:

- **چرا SSE نه polling**: polling هر ۲–۳ ثانیه بودجهٔ ریت‌لیمیت (۳۰/دقیقه)
  را می‌خورد؛ SSE یک اتصالِ واحد است و رویدادها را همان لحظه می‌رساند.
- **چرا `fetch` نه `EventSource`**: `EventSource` نمی‌تواند هدر `Authorization`
  بفرستد؛ کلاینت با `fetch` + خواندن `ReadableStream` استریم را می‌خواند و
  خط‌های `event:`/`data:` را خودش parse می‌کند (۳۰ خط، بدون کتابخانه).
- **ترتیب رویدادها**: ورکر رویدادها را هم‌زمان و مرتب پخش می‌کند (`snapshot`
  در هر تغییر وضعیت، `progress` به ترتیب تسک‌ها، دقیقاً یک `terminal`)؛ تست
  «ترتیب رویدادها» در `tests/bench_phase5.test.ts` این را قفل می‌کند.
- **امنیت**: همان احراز هویت Bearer و ریت‌لیمیتِ بقیهٔ مسیرها؛ payloadها فقط
  شمارش/عنوان تسک‌اند (نه پرامپت، نه خروجی مدل)؛ قطع اتصال، اشتراک را آزاد
  می‌کند؛ listenerای که خطا بدهد هرگز ورکر را خراب نمی‌کند.

## عمداً بیرون گذاشته شده (و چرا)

- **ورود کلید / ساخت پروایدر در وب**: کلیدها هرگز وارد مرورگر نمی‌شوند. افزودن پروایدر و وارد کردن کلید فقط از تلگرام (`/ai`)؛ داشبورد فقط فلگ‌های enable/active را تغییر می‌دهد و `hasCredential` را به‌صورت بولی نشان می‌دهد.
- **تغییر حافظه در وب**: حافظه فقط خواندنی است؛ هر تغییری همچنان از تلگرام و با تأیید curator.
- **کرون آزاد بدون سقف از وب**: کرون سفارشی فاز ۵ همیشه کف فاصله را رعایت می‌کند (بنچ‌مارک ≥ ۱ ساعت، خلاصه ≥ ۱۵ دقیقه) تا یک اشتباه/سوءاستفاده نتواند هر دقیقه agent turn یا بنچ‌مارک بسوزاند.
- **ویرایش اکشنِ زمان‌بند از وب**: وب فقط پرامپت و مقصدِ اکشنِ `agent` خلاصه را ویرایش می‌کند؛ تغییر نوع اکشن (مثلاً به `tool`) یا نام ردیف از وب ممکن نیست.
- **فایل جدا برای JS/CSS**: عمداً همه‌چیز inline است — چون ناوبری مرورگر نمی‌تواند هدر `Authorization` بفرستد، فایل جدا نمی‌توانست پشت احراز هویت توکنی بنشیند.
- **سطح عمومی**: هیچ. داشبورد صددرصد مالک است؛ هیچ مسیر عمومی ندارد.

## مدل امنیتی

1. **توکن تنها راه احراز هویت است** — همان `BOBI_API_TOKEN`، با مقایسهٔ constant-time (الگوی `server.ts`). همهٔ مسیرها، از جمله پوسته‌های HTML، توکن می‌خواهند؛ **تنها استثنا** صفحهٔ ورودِ `/dashboard` است که چون مرورگر روی ناوبری هدر نمی‌فرستد ناچاراً بدون توکن سرو می‌شود — و صفر دیتای مالک دارد (فقط یک فرم پسورد).
2. **توکن هرگز در URL نیست**: فقط هدر `Authorization: Bearer`. صفحهٔ ورود آن را در `sessionStorage` نگه می‌دارد (نه `localStorage` — با بستن تب پاک می‌شود، ماندگاری دیسکی ندارد؛ انتخاب آگاهانه: رفرش صفحه نیاز به ورود مجدد ندارد ولی تب جدید می‌خواهد)، هرگز در کوئری/کوکی. با اولین 401 توکن دور ریخته می‌شود.
3. **CSRF**: چون هیچ کوکی‌ای وجود ندارد، CSRF کلاسیک منتفی است؛ با این حال همهٔ مسیرهای تغییردهنده `POST` + `Content-Type: application/json` می‌خواهند (غیر آن → `415`) تا پستِ فرم ساده هم رد شود.
4. **Rate limit**: ۳۰ درخواست در دقیقه per-IP، **قبل** از احراز هویت (مثل `/api/v1/turn`) — کند کردن brute-force توکن.
5. **XSS**: سرور هیچ دیتای مالکی را داخل HTML تزریق نمی‌کند (پوسته‌ها استاتیک‌اند). رندر سمت کلاینت فقط از طریق `escapeHtml` / `renderSafeMarkdown` در `src/http/dashboard_render.ts` انجام می‌شود — همان سورسی که تست واحد دارد و با `.toString()` عیناً در مرورگر جاسازی شده؛ کپی دومی برای drift وجود ندارد. رندرر مارک‌داون عمداً لینک/عکس/HTML خام را پشتیبانی نمی‌کند.
6. **Path traversal**: گزارش بنچ فقط با `name`ای که (الف) با رجکس سخت‌گیرانه مچ شود و (ب) دقیقاً در لیستینگ زندهٔ دایرکتوری باشد سرو می‌شود؛ مسیر نهایی هم با `resolve` چک می‌شود که زیر `bench/results` بماند.
7. **خطاها فارسی و ژنریک‌اند** — بدون استک، بدون مقدار کانفیگ، بدون اینکه بگویند چرا احراز هویت شکست خورد.
8. **حافظه اسکوپ‌شده به مالک**: فقط `OWNER_TELEGRAM_ID`؛ اگر ست نباشد endpoint با 503 fail-closed می‌شود (خواندن حافظهٔ کاربر دیگر غیرممکن است).
9. **بن/میوت**: اعتبارسنجی شناسه دقیقاً مثل دستور `/ban` (`/^[1-9][0-9]{0,19}$/`) و مالک نمی‌تواند خودش را محدود کند.

## بررسی سطح حمله

| بردار | وضعیت |
|---|---|
| حدس توکن (brute force) | ریت‌لیمیت قبل از احراز هویت + مقایسهٔ constant-time؛ 401 ژنریک بدون تمایز «توکن نیست» از «توکن غلط است» |
| دزدیدن توکن از URL/هیستوری | توکن هرگز در URL، کوئری، یا لاگ قرار نمی‌گیرد؛ فقط هدر |
| XSS از محتوای حافظه/پروایدر/گزارش بنچ | همه‌چیز از `escapeHtml` می‌گذرد؛ رندرر مارک‌داون HTML خام و `javascript:` را خنثی می‌کند (تست‌شده) |
| XSS از لیبل‌های نمودار روند | `buildLineChartSvg` همهٔ لیبل‌ها/تیک‌ها را escape می‌کند و مختصات را اعتبارسنجی/محدود می‌کند (تست‌شده، از جمله `titleFa` حاوی `<script>`) |
| CSRF روی ban/disable/scheduler | بدون کوکی (توکن فقط هدر `Authorization` + `sessionStorage`) پس CSRF کلاسیک منتفی است؛ با این حال همهٔ مسیرهای تغییردهنده `POST` + `Content-Type: application/json` می‌خواهند (غیر آن → `415`) تا پستِ فرم سادهٔ cross-origin هم رد شود |
| Path traversal در `?name=` | رجکس + allowlist از لیستینگ زنده + چک `resolve` |
| دسترسی بدون توکن به APIها | همهٔ ۱۶ مسیر API بدون توکن 401 می‌دهند (تست برای تک‌تک مسیرها، شامل ۴ مسیر جدید فاز ۴) |
| تزریق کرون دلخواه از وب | `cadence` فقط سه کلید فهرست‌سفید؛ کرون سفارشی (فاز ۵) باید `parseCron` را پاس کند و کف فاصله را رعایت کند (بنچ‌مارک ≥ ۱h، خلاصه ≥ ۱۵min) — هر رشتهٔ دیگری → 400. `time` فقط `HH:MM` صفرپدشده با رجکس سخت‌گیرانه؛ `mode` فقط `offline`/`live` |
| نشت سکرت در دادهٔ نمودار/زمان‌بند | روندها فقط امتیاز و جمع‌بندی‌اند (نه پرامپت، نه خروجی خام مدل)؛ اکشنِ زمان‌بند هرگز به کلاینت برنمی‌گردد (فقط `mode` استخراج‌شدهٔ بنچ)؛ جزئیات audit فقط کلیدهای بی‌خطر است |
| تغییر زمان‌بندِ کاربر دیگر | همهٔ خواندن/نوشتن‌ها با `created_by_user_id = OWNER_TELEGRAM_ID` اسکوپ شده‌اند (همان `getTask`/`updateTask`/`createTask` اسکوپ‌شده)؛ بدون `OWNER_TELEGRAM_ID` مسیرها 503 fail-closed می‌دهند |
| تزریق پرامپت مخرب از وب | پرامپت فقط روی ردیفِ خلاصهٔ صبحگاهی و فقط وقتی اکشن `agent` است نوشته می‌شود؛ ولیدیشن همان `parseTaskAction` زمان‌بند (سقف ۴۰۰۰ کاراکتر)؛ نام/کرون/نوع‌اکشن ردیف از این مسیرها قابل‌نوشتن نیست؛ متن پرامپت هرگز در audit لاگ نمی‌شود |
| دور زدن مالکیت `/blueprint` از وب | UI مالکیت را نشان می‌دهد و ویرایش فقط از همان استور (`storage.updateTask`) انجام می‌شود؛ اجرای دوبارهٔ `/blueprint run morning_digest` ردیف را با پیش‌فرض بازسازی می‌کند |
| خلاصهٔ گروه برای گروهِ بیگانه | `chatId` فقط عددی و کانفیگ از پرِفِ اسکوپ‌شدهٔ مالک خوانده می‌شود؛ تسک با `created_by_user_id = OWNER` ساخته می‌شود و اکشنِ آن همیشه `group_digest` با ورودیِ فقط-خواندنی است؛ تحویل همیشه به دایرکت مالک (فیکس سمت سرور) |
| XSS از پرامپت/شناسهٔ چت در UI | همهٔ رشته‌های سرور (پرامپت، chatId، کرون) در کلاینت از `escapeHtml` می‌گذرند |
| دو بار ساختِ زمان‌بند بنچ | به‌روزرسانی درجا (update) انجام می‌شود نه ساختِ دوباره؛ تست «دقیقاً یک ردیف» این را قفل می‌کند |
| نشت دیتا از صفحهٔ ورود | صفحهٔ ورود صفر دیتای مالک دارد (تست: حافظه/پروایدر داخل HTML نیست) |
| تغییر حافظه از وب | هیچ مسیر تغییردهنده‌ای برای حافظه وجود ندارد (POST روی `/memory` → 405) |
| ورود کلید از وب | عمداً پیاده نشده؛ کلید فقط در تلگرام |
| بن کردن خودِ مالک | رد می‌شود (400)، مثل `/ban` |
| غیرفعال کردن پروایدر/مدل فعال | رد می‌شود (400) تا ران‌تایم یتیم نماند — همان قانون `ProviderService` |
| فعال‌سازی مدلِ پروایدرِ غیرفعال | رد می‌شود (400)، مثل quick-switch تلگرام |
| نشستن روی پورت جدا | داشبورد همان `Bun.serve` موجود را گسترش می‌دهد؛ listener دومی وجود ندارد |
| رفتار `/health` و `/api/v1/turn` | بدون تغییر (تست‌های `http_api.test.ts` سبز) |

## فایل‌ها

- `src/http/dashboard.ts` — روتر + همهٔ هندلرهای API (فاز ۴: روندها + زمان‌بندها؛ فاز ۵: کرون سفارشی، پرامپت/مقصد خلاصه، خلاصه‌های گروه)
- `src/http/dashboard_pages.ts` — پوستهٔ ورود + پوستهٔ SPA (تمپلیت‌های HTML با JS/CSS inline؛ فاز ۴: تب «زمان‌بندها» + سکشن نمودار روند در تب بنچ‌مارک‌ها؛ فاز ۵: فیلد کرون سفارشی، کارت ویرایش پرامپت/مقصد، تب «گروه‌ها»)
- `src/http/dashboard_render.ts` — `escapeHtml`، `renderSafeMarkdown` و `buildLineChartSvg` (خالص، تست‌شده، در کلاینت جاسازی‌شده)
- `src/storage/storage.ts` — افزودهٔ فاز ۵: `listUserPrefKeys(userId, prefix)` (فهرست کلیدهای پرِف با پیشوند، برای تب خلاصه‌های گروه)
- `tests/dashboard.test.ts` — ۱۱۹ تست (۸۲ فاز ۳/۴ + ۳۷ فاز ۵: احراز هویت مسیرهای جدید، اعتبارسنجی کرون سفارشی، مالکیت بلوپرینت، audit، و API خلاصه‌های گروه)
- تغییر کوچک در `src/http/server.ts`: هوک داشبورد قبل از 404 (افزایشی؛ بدون تغییر رفتار موجود)

## عمداً جا افتاده (فاز ۴/۵)

- **حذف فیزیکی زمان‌بند از وب**: خاموش = `enabled=false` (ردیف و تاریخچه حفظ می‌شود)؛ حذف کامل همچنان با `/bench schedule off` یا `cancel_task` تلگرام. (استثنا: خاموش‌کردن خلاصهٔ گروه از وب ردیف تسک آن گروه را پاک می‌کند — دقیقاً همان معناشناسی `/gassistant digest off`، چون کانفیگِ خاموش + ردیفِ مانده معنا ندارد.)
- **کرون سفارشی برای خلاصهٔ گروه از وب**: خلاصهٔ گروه فقط `HH:MM` روزانه می‌پذیرد (همان سطح تلگرام)؛ کرون سفارشی فقط برای دو زمان‌بند مدیریتی (بنچ‌مارک + خلاصهٔ صبحگاهی) است.
- **روشن‌کردن حالت دستیار گروه از وب**: وب فقط خلاصهٔ گروه‌هایی را مدیریت می‌کند که حالتشان از تلگرام روشن شده (`need_mode`)؛ خودِ `/gassistant on` وب ندارد.
