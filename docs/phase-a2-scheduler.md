# فاز A2 — زمان‌بند وظایف (Scheduled Tasks)

زمان‌بند یادآورها حالا یک سیستم **زمان‌بندی عمومی** شده: وظایفی که با عبارت کرون
تعریف می‌شوند، در زمان مقرر یک **اکشن ساخت‌یافته** اجرا می‌کنند — اجرای ابزار،
ارسال پیام، یا اجرای ایجنت. API یادآورها (`remind_at` و دوستان) دست‌نخورده مانده؛
این فاز فقط اضافه کرده است.

## عبارت کرون

پنج فیلد، با فاصله از هم جدا می‌شوند:

```
دقیقه ساعت روزِ_ماه ماه روزِ_هفته
  0     9      *        *     MON-FRI
```

- هر فیلد: `*`، لیست (`1,15,30`)، بازه (`9-17`)، گام (`*/15` یا `1-30/5`)
- نام‌ها (case-insensitive): ماه‌ها `JAN` تا `DEC`، روزها `MON` تا `SUN`
- در روزِ هفته، `0` و `7` هر دو یکشنبه‌اند
- میان‌بُرها: `@hourly` ،`@daily` (و `@midnight`)، `@weekly` ،`@monthly`
- هر چیز دیگری با `@` شروع شود (مثل `@reboot`) رد می‌شود

نمونه‌ها:

| عبارت | معنی |
|---|---|
| `0 9 * * *` | هر روز ساعت ۹ صبح |
| `*/15 9-17 * * MON-FRI` | روزهای کاری، هر ۱۵ دقیقه بین ۹ تا ۱۷ |
| `0 0 1 * *` | اول هر ماه، نیمه‌شب |
| `30 8 * * 1-5` | روزهای کاری ساعت ۸:۳۰ |
| `@weekly` | یکشنبه‌ها نیمه‌شب |

**نکته‌ی روزِ ماه / روزِ هفته:** اگر *هر دو* محدود شده باشند (نه `*`)، روزی که
**یکی**‌شان بخورد کافی است (رفتار استاندارد Vixie cron). اگر فقط یکی محدود باشد،
همان تصمیم می‌گیرد.

**منطقه‌ی زمانی:** عبارت در یک IANA timezone تفسیر می‌شود (پیش‌فرض: منطقه‌ی
زمانی بات، معمولاً `Asia/Tehran`). ساعت دیواری همان می‌ماند: «هر روز ۹ صبح» با
تغییر ساعت تابستانی جابه‌جا نمی‌شود. ساعتی که در گذار بهار وجود ندارد (مثل
۲:۳۰ در روزی که ساعت جلو می‌رود) رد می‌شود و به روز بعد می‌رسد.

اعتبارسنجی سخت‌گیرانه است: فیلد کم یا زیاد، عدد خارج از بازه، گام صفر، بازه‌ی
وارونه (`5-1`)، آیتم خالی (`1,,2`)، یا گامِ تنها (`5/15`) همه با خطای واضح رد
می‌شوند — زمان‌بندیِ اشتباهِ بی‌صدا بدتر از رد شدنِ بلند است.

## ابزارها (فقط مالک)

| ابزار | کار |
|---|---|
| `schedule_task` | ساخت وظیفه: `name`، `cron`، `timezone` (اختیاری)، `action` (آبجکت)، `enabled` (اختیاری) |
| `list_tasks` | فهرست وظایف، به ترتیب نزدیک‌ترین اجرای بعدی |
| `cancel_task` | حذف وظیفه با شناسه |

سقف‌ها: حداکثر **۲۵** وظیفه برای مالک، نام حداکثر ۸۰ کاراکتر، اکشن حداکثر
۸ کیلوبایت.

## اکشن‌ها

اکشن یک آبجکت ساخت‌یافته است — **هرگز کد نیست و eval نمی‌شود**:

```jsonc
// اجرای ابزار، با ورودیِ داده‌شده
{ "type": "tool", "tool": "calculator", "input": { "op": "add", "a": 2, "b": 3 } }
// ارسال پیام به یک چت
{ "type": "message", "chatId": "123456", "text": "صبح بخیر ☀️" }
// اجرای ایجنت روی یک پرامپت، و تحویل جواب به چت
{ "type": "agent", "chatId": "-100123", "prompt": "خلاصه‌ی خبرهای امروز" }
```

قواعد اعتبارسنجی:

- `tool`: نام باید snake_case معتبر باشد، ابزار باید ثبت‌شده باشد، و
  **`schedule_task` نمی‌تواند اکشن یک وظیفه باشد** — وظیفه‌ای که وظیفه بسازد
  بدون مرز رشد می‌کند.
- `message`: متن ۱ تا ۲۰۰۰ کاراکتر.
- `agent`: پرامپت ۱ تا ۴۰۰۰ کاراکتر.
- اکشن هم موقع ساخت و هم **موقع اجرا** دوباره اعتبارسنجی می‌شود؛ ردیفی که از
  اعتبارسنجی رد نشود اجرا نمی‌شود (وضعیت `failed` می‌گیرد) اما زمان‌بندی را قفل
  نمی‌کند.

## چرخه‌ی اجرا

1. هر تیک (پیش‌فرض ۳۰ ثانیه)، وظایفِ رسیده (`enabled` و `next_run_at <= now`)
   خوانده می‌شوند.
2. هر وظیفه **اتمی** تصاحب (claim) می‌شود: آپدیتِ `next_run_at_ms` فقط وقتی موفق
   است که مقدار قبلی همان اسلاتی باشد که خوانده شده — پس دو گذر هم‌زمان هرگز
   یک وظیفه را دو بار اجرا نمی‌کنند.
3. تصاحب، **همان‌جا** اسلات بعدی را هم می‌نویسد (از روی عبارت کرون، نه از روی
   `now`، تا سری جابه‌جا/drift نشود). اگر پروسس بین تصاحب و اجرا بمیرد، آن یک
   نوبت از دست می‌رود اما هرگز دو بار اجرا نمی‌شود — همان معامله‌ای که یادآورها
   می‌کنند (تکرارِ ارسال بدتر از تأخیر است).
4. نتیجه در `last_status` (`ok` / `failed` / `skipped`) و `last_run_at_ms` ثبت
   می‌شود و `run_count` یکی اضافه می‌شود.

## سیاست عقب‌افتادگی (catch-up)

مثل یادآورها، برای بوت شدن بعد از قطعی:

- وظیفه‌ای که حداکثر **۱ ساعت** از اسلاتش گذشته باشد: **یک بار** اجرا می‌شود، بعد
  به اسلات بعدی می‌رود.
- وظیفه‌ای که بیشتر از ۱ ساعت عقب باشد: **اجرا نمی‌شود** (`skipped`) و مستقیم
  به نزدیک‌ترین اسلات آینده می‌پرد — پخشِ یکجایِ نوبت‌های ازدست‌رفته نویز است،
  نه یادآوری.

## مدل امنیتی

- **ساخت/فهرست/حذف فقط برای مالک است**، در دو لایه: پرچم `ownerOnly` روی ابزار
  باعث می‌شود پلِ احراز هویت کلید دسترسی را به غیرمالک ندهد (ابزار برای مدل هم
  نامرئی می‌ماند)، و بدنه‌ی `run()` مالکیت را با یک تابعِ سمت‌سرور دوباره چک
  می‌کند — پس بازیگری که دستی ساخته شده هم رد می‌شود.
- **اکشن ابزار با مجوزهایِ زنده‌ی سازنده اجرا می‌شود** (`created_by_user_id`)،
  که هر بار از نو ساخته می‌شود — نه چیزی که در ردیف ذخیره شده، نه چیزی که مدل
  گفته. چون فقط مالک می‌تواند وظیفه بسازد، این یعنی تفویضِ اختیارِ خودِ مالک به
  زمان‌بندی‌ای که خودش نوشته؛ لغو دسترسی بین زمان ساخت و اجرا، در اجرای بعدی
  اثر می‌کند.
- **پیام‌ها موقع تحویل دوباره چک می‌شوند**: اگر گیرنده دیگر تأییدشده نباشد،
  پیام فرستاده نمی‌شود (مثل یادآورها).
- اکشن‌ها ساخت‌یافته‌اند: بدون shell، بدون eval، با سقف حجم (۸KB) و **تایم‌اوت
  جداگانه برای هر اجرا** (پیش‌فرض ۳۰ ثانیه).
- اکشن `agent` به موتور گفتگو وصل است؛ اگر رانر تزریق نشده باشد، وظیفه `failed`
  می‌شود با دلیلِ واضح، نه کرش.
