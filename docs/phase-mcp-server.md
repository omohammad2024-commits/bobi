# فاز MCP server — بابی به‌عنوان سرور MCP

بابی حالا می‌تواند خودش را به‌عنوان یک سرور MCP عرضه کند (معادل
`hermes mcp serve` در هرمس): ابزارهای استاندارد برای کلاینت‌های محلیِ قابل
اعتماد مثل Claude Code و Cursor — فهرست مکالمات، خواندن تاریخچه، ارسال پیام
و وضعیت مکالمه. این، آینهٔ `src/mcp/bridge.ts` است: آن فایل کلاینت MCP بابی
است (ابزار سرورهای دیگر را مصرف می‌کند)، این فاز بابی را به **سرور** تبدیل
می‌کند (دیگران ابزارهای بابی را مصرف می‌کنند).

قرارداد در `tests/mcp_server.test.ts` پین شده است (۲۲ تست).

## فایل‌ها

| فایل | نقش |
|---|---|
| `src/mcp/server.ts` | پیاده‌سازی سرور: `createMcpServer(deps)` — JSON-RPC 2.0 روی stdio با متدهای `initialize`، `tools/list`، `tools/call` |
| `src/mcp/serve.ts` | ورودی اجرایی: `bun src/mcp/serve.ts` — سیم‌کشی واقعی (کانفیگ، دیتابیس، پروایدر، موتور)؛ `src/index.ts` دست نخورده |
| `src/storage/storage.ts` | دو متد افزوده‌شده: `listUserConversations` و `countMessages` (+ اینترفیس `UserConversationSummary`) |
| `src/conversation/engine.ts` | یک متد افزوده‌شده: `isConversationRunning` (خوانش افزودنی از نقشهٔ `running`) |

## ابزارها

| ابزار | ورودی | خروجی |
|---|---|---|
| `bobi_list_conversations` | `userId` | آرایه‌ای از `{ conversationId, lastActivity, messageCount }` — جدیدترین فعالیت اول |
| `bobi_read_history` | `userId`, `conversationId`, `limit` (پیش‌فرض ۵۰، سقف ۲۰۰) | پیام‌های اخیر به ترتیب زمانی: `{ role, content, createdAt }` |
| `bobi_send_message` | `userId`, `conversationId`, `text` (سقف ۸۰۰۰ نویسه) | `{ reply, model, isFake, toolCalls }` — یک نوبت کامل موتور مکالمه که در تاریخچه هم ذخیره می‌شود |
| `bobi_conversation_status` | `userId`, `conversationId` | `{ status: "running" \| "idle", messageCount }` |

شناسهٔ مکالمه همان `chat_id` است — همان رشته‌ای که `ConversationEngine`
به‌عنوان `conversationId` استفاده می‌کند.

## پروتکل

- قاب‌بندی stdio طبق استاندارد MCP: هر پیام JSON روی یک خط از stdin، هر پاسخ
  یک JSON روی یک خط از stdout.
- `initialize` نسخهٔ پروتکل `2024-11-05` و `serverInfo: { name: "bobi-mcp" }`
  را اعلام می‌کند؛ `notifications/initialized` بدون پاسخ رها می‌شود.
- خطاها طبق JSON-RPC 2.0: JSON نامعتبر ← `-32700`، پیام غیرپروتکلی ←
  `-32600`، متد ناشناخته ← `-32601`، ابزار ناشناخته یا ورودی نامعتبر ←
  `-32602`. خطای سطح ابزار (مثلاً ورودی نامعتبر یا خطای موتور) با
  `isError: true` برمی‌گردد تا کلاینت بتواند آن را به کاربرش نشان دهد.
- یک خط خراب هرگز سرور را از پا نمی‌اندازد: پاسخ خطای parse برمی‌گردد و
  جلسه ادامه پیدا می‌کند.

## مدل امنیتی و سطح حمله

1. **کلاینت‌ها ابزارهای محلیِ مورد اعتمادند، ولی درخواست‌کننده صاحب اختیار
   نیست.** `bobi_send_message` همیشه با نقش **مالک** اجرا می‌شود: سطح دسترسی
   ابزارها از `ownerActor` می‌آید که موقع راه‌اندازی، سمت سرور، با
   `authorizeToolUse` و هویت واقعی مالک ساخته شده (`src/mcp/serve.ts`) —
   درخواست فقط `userId` (کدام فضای مکالمه) و متن را انتخاب می‌کند، هرگز
   مجوزها را. بدون `ownerActor`، نوبت بدون هیچ دسترسی ابزاری اجرا می‌شود
   (fail-closed) ولی خود پاسخ همچنان کار می‌کند.
2. **جداسازی هر کاربر در لایهٔ ذخیره‌سازی.** هر سه خوانش
   (`listUserConversations`، `history`، `countMessages`) روی `user_id` فیلتر
   می‌کنند: کاربر A با حدس شناسهٔ مکالمهٔ کاربر B چیزی نمی‌بیند — تاریخچه
   خالی و شمارش صفر برمی‌گردد، نه خطایی که وجود مکالمه را لو بدهد.
3. **مرز اعتماد، stdio است.** فقط stdio پیاده شده؛ عرضه روی شبکه عمداً خارج
   از محدوده است. هر کس بتواند روی stdin این پروسس بنویسد، عملاً با همان
   کاربر سیستم‌عاملِ بات اجراست.
4. **ورودی‌ها محدودند.** `userId`/`conversationId` رشتهٔ غیرخالی با سقف طول
   (۶۴/۱۲۸)؛ `limit` به بازهٔ ۱ تا ۲۰۰ clamp می‌شود؛ متن پیام سقف ۸۰۰۰
   نویسه دارد. شناسه‌ها به‌صورت پارامتر bound به SQL می‌روند.
5. **`status` موتور واقعی را نشان می‌دهد.** پرچم `running` همان نقشهٔ
   داخلی‌ای است که `cancel()` بات هم از آن می‌خواند؛ پس نوبتی که از تلگرام
   شروع شده هم این‌جا `running` دیده می‌شود، نه فقط نوبت‌های خود MCP.

## سیم‌کشی اجرایی (`src/mcp/serve.ts`)

عمداً مینیمال است: همان `loadConfig`، همان دیتابیس (`Storage.open`)، همان
انتخاب پروایدر بات (gateway با پروایدرهای پیکربندی‌شدهٔ مالک، و در نبود آن
`FakeProvider`)، و یک `ConversationEngine` با ابزارهای هسته (بدون
سیم‌کشی اضافهٔ `src/index.ts` مثل پنل‌ها و زمان‌بندها). غنی‌سازی بعدی
(ابزارهای حافظه، مهارت‌ها، ابزارهای کلاینت MCP) این‌جا اضافه می‌شود، بدون
تغییر در `src/mcp/server.ts`.

اتصال از کلاینت محلی، مثلاً:

```json
{ "mcpServers": { "bobi": { "command": "bun", "args": ["src/mcp/serve.ts"] } } }
```

## نکتهٔ پیاده‌سازی

تغییرات `storage.ts` و `engine.ts` کاملاً افزودنی‌اند: هیچ API عمومی یا
رفتار پیش‌فرضی عوض نشده. اسکیمای دیتابیس دست نخورده (فقط SELECTهای جدید)،
پس نیازی به مایگریشن نیست.
