# دستورهای سیستمی مالک (Phase: Commands System)

۱۹ دستور مدیریتی بابی — همه **فقط برای مالک** — در `src/bot/cmd_system.ts`
(رشته‌ها در `src/bot/cmd_system_strings.ts`، تست‌ها در `tests/cmd_system.test.ts`).
ثبت‌کننده: `registerSystemCommands(bot, deps, opts)`؛ هماهنگ‌کننده باید آن را
در `createBot` کنار ماژول‌های خواهر صدا بزند و `COMMAND_DEFS` را در
`setMyCommands` ادغام کند.

## فهرست دستورها

| دستور | کار |
|---|---|
| `/snapshot` | ساخت/فهرست/بازگردانی اسنپشات وضعیت (کپی فایل SQLite) |
| `/restart` | راه‌اندازی مجدد (خروج با کد ۰؛ systemd بالا می‌آورد) |
| `/update` | `git pull --ff-only` و سپس راه‌اندازی مجدد (نشانگر تایپینگ در حین pull) |
| `/debug` | گزارش اشکال‌زدایی به‌صورت فایل `.md` (با سانسور اسرار) |
| `/usage` | مصرف توکن امروز + ۷ روز، با هشدار «تقریبی بودن هزینه» |
| `/insights` | تحلیل مصرف N روزه (پیش‌فرض ۷، سقف ۳۰): روزانه، مدل‌های پرمصرف، روند |
| `/model` | نمایش مدل فعال + دکمه‌های لمسی تعویض سریع (`mdl:switch:<id>`)؛ `/model <name>` تعویض مدل |
| `/reasoning` | نمایش/تنظیم سطح استدلال |
| `/autoprune` | نمایش/تنظیم حذف خودکار نشست‌ها (فقط ثبت نیت؛ اجرای واقعی پیگیری هماهنگ‌کننده) |
| `/tools` | فهرست ابزارهای ثبت‌شده با toolset و وضعیت فعال‌بودن (فقط فهرست) |
| `/skills` | فهرست مهارت‌های نصب‌شده (نام + توضیح کوتاه؛ بدنهٔ مهارت برنمی‌گردد) |
| `/curator` | `status` (تعداد پیشنهادهای در انتظار) و `run` (اجرای ابزار `curate_memories` + نشانگر تایپینگ) |
| `/plugins` | فهرست افزونه‌های نصب‌شده |
| `/reload_mcp` | اتصال مجدد سرورهای MCP |
| `/reload_skills` | بازخوانی پوشهٔ مهارت‌ها |
| `/approve` | تأیید درخواست عضویت کاربر/گروهِ در انتظار |
| `/deny` | رد درخواست عضویت کاربر/گروهِ در انتظار |
| `/sethome` | ثبت این گفت‌وگو به‌عنوان کانال اصلی اعلان‌های فعال |
| `/pause` | توقف اضطراری (`/pause on\|off`) — فقط پرچم؛ اتصال به زمان‌بند پیگیری هماهنگ‌کننده |

## الگوی تأیید (`--confirm`)

همهٔ عملیات مخرب از یک الگوی یکسان پیروی می‌کنند: **فراخوانی اول فقط توضیح
می‌دهد و دستورِ دقیقِ تأیید را چاپ می‌کند؛ اجرای واقعی فقط با `--confirm`:**

- `/snapshot restore <name> --confirm`
- `/restart --confirm` (و `/restart --force --confirm` وقتی گفت‌وگویی در حال اجراست)
- `/update --confirm`
- `/approve <user|group> <id> --confirm` و `/deny <user|group> <id> --confirm`

## نکتهٔ remap: `/approve` و `/deny`

در هرمس این دو دستور فراخوانیِ ابزارِ وسطِ turn را تأیید/رد می‌کردند. سطح
تأییدِ در انتظارِ واقعیِ بابی، گیت‌های دسترسی کاربر و گروه‌اند
(`UserAccessService` / `GroupAccessService`)؛ پس معنای دستورها به همین سطح
remap شده: تأیید یا رد **درخواست‌های عضویت در انتظار**. هر تصمیم موفق در
`audit_log` ثبت می‌شود.

## شکاف‌های صادقانه (documented gaps)

1. **`/tools` فقط فهرست است.** `ToolRegistry` متد عمومیِ فعال/غیرفعال‌کردن
   ندارد؛ رجیستری فقط در زمان ثبت ساخته می‌شود.
2. **`/reasoning`: سطحِ مؤثر از env خوانده می‌شود.** آداپترها در هر درخواست
   `resolveReasoningEffort()` (متغیر `BOBI_REASONING_EFFORT`) را صدا می‌زنند و
   هیچ seam در سطح فراخوانی برای pref کاربر وجود ندارد. دستور، سطح مؤثر فعلی را
   نشان می‌دهد و انتخاب مالک را در pref `reasoning_effort` به‌عنوان مقدار
   «مرحله‌بندی‌شده» ذخیره می‌کند؛ **اعمال زنده نیازمند تنظیم env و راه‌اندازی
   مجدد است** — و این صراحتاً در خروجی گفته می‌شود.
3. **`/model`: متد switch آماده‌ای در سرویس وجود ندارد.** مسیر canonical همان
   منطق `ai_select_model` در `ai_controller.ts` است (اعتبارسنجی فعال‌بودن مدل و
   پروایدر، بعد `storage.setRuntimeSelection`). دستور دقیقاً همین اعتبارسنجی را
   تکرار می‌کند. گیت‌وی انتخاب را در هر درخواست از دیتابیس می‌خواند، پس تعویض
   بلافاصله اثر دارد و نیازی به restart نیست.
4. **`/reload_mcp`:** متد اختصاصیِ `reload()` در `McpManager` وجود ندارد؛
   بارگذاری مجدد یعنی `closeAll()` + `connectAll()` — اتصال مجدد واقعی روی
   همان پیکربندی، نه no-op.
5. **`/reload_skills`:** متد `invalidate` در `SkillCache` وجود ندارد؛
   `skills()` با تغییر mtime پوشه خودکار تازه می‌شود و این دستور همان خوانش را
   اجباری و تعداد را گزارش می‌کند.
6. **`/autoprune` و `/pause`:** فقط نیت/پرچم را ثبت می‌کنند. جاب واقعیِ حذف و
   اتصال پرچم `isPaused()` به زمان‌بند/ضربان‌قلب، پیگیری هماهنگ‌کننده است.
7. **`/snapshot`:** کپیِ فایل اصلی + sidecarهای `-wal`/`-shm`؛ بازگردانی وقتی
   turnای در حال اجراست رد می‌شود، و بعد از restore باید `/restart` زد.
   (اگر `dbPath` برابر `:memory:` باشد، اسنپشات رد می‌شود.)

## اتصال در `createBot` (برای هماهنگ‌کننده)

```ts
registerSystemCommands(bot, deps, {
  dbPath: config.dbPath,          // برای /snapshot
  mcp,                            // برای /reload_mcp
  skills,                         // برای /skills و /reload_skills
  proposalStore,                  // برای /curator status
  isAnyTurnRunning: () => /* خوانش turnهای فعال */,
});
```

بدون این wiring، دستورهای مربوطه به‌جای خطا، «در دسترس نیست» را صادقانه
گزارش می‌کنند.

## SECURITY — سطح حمله

- **اجبار مالک در سطح handler، نه منو.** هر wrapper ابتدا `isOwnerSender` را
  چک می‌کند و غیرمالک پاسخ فارسی «فقط برای مالک» می‌گیرد — حتی اگر منو پنهان
  نباشد یا دستور مستقیم تایپ شود. بدون auth، fail-closed است (هیچ‌کس مالک
  نیست).
- **`/update` کد را به‌عنوان کاربر سرویس اجرا می‌کند.** فرض اعتماد: مالک، VM
  و remote مخزنِ خودش را کنترل می‌کند. `git pull --ff-only` هرگز auto-merge
  نمی‌کند؛ pull ناموفق هرگز restart نمی‌زند. remote مخرب می‌تواند بعد از
  restart کد مخرب با اختیارات بات اجرا کند — این ریسکِ ذاتیِ به‌روزرسانی
  خودکار است و باید آگاهانه پذیرفته شود.
- **`/debug` هیچ‌وقت راز لو نمی‌دهد.** خطوط لاگ (و هر متن دیگری در باندل) پیش
  از ارسال از `scrubSecrets()` می‌گذرند. فهرست سانسور:
  1. کلیدهای `sk-…`؛ ۲. توکن‌های بات تلگرام (`123456:AAA…`)؛ ۳. توکن‌های
     گیت‌هاب (`ghp_…` و خانواده)؛ ۴. توکن‌های اسلک (`xoxb-…`)؛ ۵. کلیدهای AWS
     (`AKIA…`)؛ ۶. جفت‌های `api_key=…` / `token: …` / `password=…` و مشابه؛
     ۷. فیلدهای JSON مثل `"apiKey": "…"`؛ ۸. هدرهای `Authorization: Bearer …`.
- **محافظت در برابر traversal در اسنپشات.** نام‌ها با allow-list سخت‌گیرانه
  اعتبارسنجی می‌شوند (ASCII، بدون `..`، بدون جداکنندهٔ مسیر، حداکثر ۶۴
  کاراکتر) و همیشه زیر پوشهٔ اسنپشات‌ها join می‌شوند.
- **بدون راز در پاسخ‌ها.** هیچ دستوری کلید، توکن یا محتوای `.env` را چاپ
  نمی‌کند؛ `/debug` فقط برچسب پروایدر/مدل را نشان می‌دهد، نه credential را.
- **حسابرسی.** `snapshot.restore`، `restart`، `update` و تصمیم‌های approve/deny
  در `audit_log` ثبت می‌شوند (best-effort؛ خرابی audit دستور را نمی‌شکند).
- **`/pause` fail-closed است:** اگر خوانش pref در ثبت ناموفق باشد، پرچم خاموش
  می‌ماند (ربات در حال اجرا).
- متدهای storage استفاده‌شده همگی موجود و خواندنی‌اند:
  `usageTotalsAll`، `usageByModelAll`، `getUserPref`/`setUserPref`،
  `getRuntimeSettings`، `setRuntimeSelection`، `listProviders`/`listModels`،
  `countPending`/`countApproved` روی سرویس‌های users/groups، و `appendAudit`.
  متدِ گمشده‌ای برای این پکیج لازم نبود.
