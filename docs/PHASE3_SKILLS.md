# مهارت‌های نصب‌شدنی از داخل چت (فاز ۳، آیتم ۵)

> نصب مهارت جدید برای بابی، بدون دست‌کاری سرور: مالک یک فایل `.md` می‌فرستد یا یک نشانی می‌دهد، کارت بررسی را می‌بیند، تأیید می‌کند — و مهارت همان لحظه فعال می‌شود، بدون راه‌اندازی مجدد.

## جریان نصب (قدم‌به‌قدم)

1. **ورودی** — دو منبع، یک خط لوله:
   - فایل `.md` که مالک به‌عنوان document می‌فرستد (کپشن `/skill install`، یا ریپلایِ `/skill install` به پیام حاوی فایل)؛
   - نشانی: `/skill install https://…`
2. **اعتبارسنجی** (`src/skills/install.ts` → `prepareSkillInstall`): سقف حجم، پارس frontmatter با همان پارسر لودر، نام kebab-case، عدم تداخل نام، سقف تعداد. هر خطایی = پیام فارسی روشن، بدون نصب.
3. **اسکن ریسک** (`scanSkillBody`): بدنه از نظر تزریق پرامپت علیه ایجنت («ignore all previous instructions»، «reveal your system prompt»، معادل‌های فارسی) و محتوای شبه‌رمز (`api_key:` و…) بررسی می‌شود. نتیجه بلاک نیست — **هشدار روی کارت بررسی** است.
4. **کارت بررسی**: نام، توضیح، تریگرها، حجم، منبع، هشدارها، ۲۰ خط اول بدنه + دکمه‌های **تأیید ✅ / رد ❌**. نصب فقط با تأیید صریح.
5. **نصب**: فایل `<name>.md` در پوشهٔ مهارت‌ها نوشته می‌شود. `SkillCache` با تغییر mtime پوشه خودش را تازه می‌کند — بدون ری‌استارت. اگر مهارت هم‌نامی بود، جایگزینی فقط با تأیید صریح (دکمه یا `--confirm`).

## قوانین اعتبارسنجی

| قانون | رفتار |
|---|---|
| حجم بیش از `SKILLS_MAX_FILE_BYTES` (۶۴KB) | رد، قبل از دانلود کامل (فایل: `file_size`؛ نشانی: `content-length` + قطع استریم) |
| frontmatter خراب / بدون `name` یا `description` | رد (همان قانون strict لودر) |
| نام غیر kebab-case | رد |
| تداخل نام با مهارت موجود (فعال یا غیرفعال) | کارت بررسی با اخطار جایگزینی؛ نصب فقط با تأیید صریح |
| بیش از `SKILLS_MAX_SKILLS` (۱۰۰) | رد |
| بدنهٔ حاوی الگوی تزریق/رمز | هشدار روی کارت، نه رد خودکار |

## طراحی کارت بررسی

```
📦 بررسی مهارت جدید

نام: memory-coach
توضیح: …
تریگرها: memory, habits
حجم: 3.2 KB
منبع: فایل ارسالی / https://…

⚠️ هشدارهای امنیتی (قبل از تأیید بخوان):
• tells the agent to ignore or disregard previous instructions
  «…Ignore all previous instructions…»

پیش‌نمایش (۲۰ خط اول):
…

نصب فقط با تأیید صریح تو انجام می‌شود.
[✅ تأیید] [❌ رد]
```

توکن تأیید ۱۲۸ بیتی، یک‌بارمصرف، ۱۰ دقیقه اعتبار. دکمه‌ها بعد از تصمیم با ویرایش پیام جمع می‌شوند (دابل‌کلیک بی‌اثر). لحظهٔ تأیید، اعتبارسنجی **دوباره** اجرا می‌شود (پوشه ممکن است از زمان نمایش کارت عوض شده باشد).

## مدیریت

| دستور | اثر |
|---|---|
| `/skill show <نام>` | توضیح، تریگرها، وضعیت، ۲۰ خط اول |
| `/skill enable <نام>` / `/skill disable <نام>` | تغییرنام به/از `.disabled-<name>.md` — لودر فایل‌های مخفی را نادیده می‌گیرد، پس بدون تغییر لودر |
| `/skill uninstall <نام>` | کارت تأیید دومرحله‌ای (دکمه 🗑️ یا `--confirm`)، بعد حذف فایل |

همه زیر `/skill` (تک‌جمع با `/skills` که فقط فهرست می‌کند و دست‌نخورده مانده).

## بررسی سطح حمله (مهم‌ترین بخش این آیتم)

**۱. SSRF در fetch نشانی** — همان وضعیت `fetch_url` بازتولید شده، نه بازنویسیِ شل:
- `resolveTarget`: طرح http/https، بدون userinfo، DNS resolve و **طبقه‌بندی تک‌تک آدرس‌ها** (loopback، RFC1918، link-local مثل `169.254.169.254`، multicast…)؛ پیش‌فرض فقط عمومی (`allowLocalTargets: false`).
- سوکت فقط به آدرس تأییدشده وصل می‌شود (اتصال مستقیم به IP، بدون DNS مجدد — race rebinding بسته است؛ روی این ران‌تایم گزینهٔ `lookup` سفارشی نادیده گرفته می‌شود، پس pinning با آدرس صریح انجام شد). Host اصلی در هدر `Host` و SNI حفظ می‌شود.
- ریدایرکت‌ها (سقف ۳) دستی دنبال می‌شوند و **هر hop دوباره از صفر اعتبارسنجی می‌شود** — نشانی عمومی که به metadata داخلی ریدایرکت کند، همان‌جا می‌میرد.
- `content-type` روی هدرها چک می‌شود (فقط `text/plain`، `text/markdown`، `text/x-markdown`، `application/json`)؛ HTML رد می‌شود چون frontmatter را نابود می‌کند.
- سقف حجم **قبل از اتمام دانلود**: `content-length` بالای سقف همان اول رد می‌شود و استریم بدنه لحظهٔ عبور از سقف قطع می‌شود.

**۲. محتوای مخرب علیه ایجنت** — بدنهٔ مهارت وارد system prompt می‌شود، پس ذاتاً سطح اعتماد «دستور مالک» را دارد. دفاع: اسکن الگوهای override (انگلیسی + فارسی)، نمایش دقیق snippet مشکوک روی کارت بررسی، و **نصبِ بی‌صدا ممنوع** — حتی با `--confirm`، اگر هشداری باشد کارت بررسی اجباری است.

**۳. name-squat** — نام فایل فقط از `name` اعتبارسنجی‌شده (kebab-case) ساخته می‌شود؛ نام فایل آپلودشده و URL هیچ‌وقت به فایل‌سیستم نمی‌رسند (`../` ناممکن). تداخل نام = جایگزینی فقط با تأیید صریح. اسکوات روی مهارت‌های پلاگین بی‌اثر است (مهارت پوشه همیشه می‌برد).

**۴. بدون اجرای کد، همیشه** — مهارت فقط markdown است؛ هیچ مسیری آن را به کد تبدیل نمی‌کند. لودر/رجیستری/سرچ بدون تغییر رفتار برای مهارت‌های موجود.

**۵. مالک‌محور** — هر هندلر و هر کال‌بک (`ph3skill:…`) اول `isOwnerSender` را چک می‌کند؛ توکن به‌تنهایی اختیار نیست و روی ریجکت، pending مصرف نمی‌شود. دستور در `COMMAND_DEFS` با `ownerOnly: true` ثبت می‌شود تا در منوی عمومی نامرئی بماند.

## نکته برای هماهنگ‌کننده (وایرینگ)

- `registerPhase3SkillsCommands(bot, deps, opts)` را صدا بزن؛ `COMMAND_DEFS` را به منو merge کن. این ماژول خودش در `index.ts`/`bot.ts` ثبت نشده.
- `opts`: `{ skills }` (همان `SkillCache` سراسری)، `{ skillsDir }` (اختیاری، پیش‌فرض پوشهٔ کش)، `{ fetcher }` (اختیاری)، `{ botToken }` برای دانلود document، `{ downloadDocument }` برای تست.
- ترتیب `message:document`: اگر هندلر ایجنت قبل از این ماژول document را مصرف کند، نصب با کپشن کار نمی‌کند — ترتیب ثبت را طوری بچین که این هندلر اول ببیند یا مستند کن.

## عمداً جا افتاده (و چرا)

- **مارکت‌پلیس عمومی/اشتراک‌گذاری مهارت بین کاربران**: خارج از اسکوپ — این آیتم «شخصی» تعریف شده؛ اشتراک‌گذاری یعنی اعتماد به محتوای دیگران و مدل امنیتی جدا می‌خواهد.
- **امضای دیجیتال مهارت‌ها**: برای منبع شخصی (فایل خود مالک / URLای که خودش داده) هزینه‌اش بیش از فایده است؛ کارت بررسی + اسکن، نقطهٔ اعتماد است.
- **ویرایش مهارت از چت**: با uninstall + install پوشش داده می‌شود؛ ویرایش in-place ریسک ناهماهنگی review/install را برمی‌گرداند.
- **نصب خودکار از URL بدون کارت** (حتی با `--confirm` وقتی هشدار هست): عمداً ممنوع — هشدار باید دیده شود.
- **تغییر لودر/رجیستری**: additive-first؛ رفتار مهارت‌های موجود و تست‌هایشان دست‌نخورده.
