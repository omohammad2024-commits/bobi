# وب‌هوک‌های خروجی (Outbound Webhooks)

BOBI می‌تواند رویدادهای چرخه‌ی عمر ایجنت را به‌صورت POST امضاشده (HMAC-SHA256)
به URLهایی که مالک بات پیکربندی کرده ارسال کند — مثلاً برای داشبورد هزینه،
لاگ متمرکز، یا اتوماسیون‌های شخصی. این قابلیت **به‌طور پیش‌فرض خاموش** است و
فقط با تنظیم متغیرهای محیطی فعال می‌شود.

## پیکربندی

| متغیر | توضیح |
|---|---|
| `BOBI_WEBHOOK_URL` | یک یا چند URL مقصد، جدا شده با ویرگول (اختیاری) |
| `BOBI_WEBHOOK_SECRET` | کلید مشترک امضا — وقتی URL تنظیم شده **اجباری** است |

قانون fail-closed: اگر `BOBI_WEBHOOK_URL` تنظیم شده ولی `BOBI_WEBHOOK_SECRET`
خالی باشد، وب‌هوک‌ها **غیرفعال** می‌مانند، یک هشدار لاگ می‌شود و هیچ درخواستی
— امضاشده یا بدون امضا — ارسال نمی‌شود. ارسال بدون امضا از سکوت بدتر است، چون
گیرنده anyway نمی‌توانست اصالت رویداد را تأیید کند.

## رویدادها

پوشه (`envelope`) هر رویداد دقیقاً این شکل را دارد:

```json
{
  "event": "agent:start",
  "at": "2026-10-18T13:00:00.000Z",
  "conversationId": "chat-1",
  "userId": "u-1",
  "data": { "model": "…", "hasAttachments": false, "userTextLength": 42 }
}
```

| رویداد | کی ارسال می‌شود | محتوای `data` |
|---|---|---|
| `agent:start` | قبل از شروع حلقه‌ی ایجنت | مدل، داشتن پیوست، **طول** متن کاربر |
| `agent:end` | بعد از پایان حلقه (موفق یا ناموفق) | مدت‌زمان، تعداد ابزارها، موفق/ناموفق، دلیل توقف، تعداد توکن‌ها |
| `tool:end` | بعد از هر اجرای ابزار | نام ابزار، وضعیت، مدت‌زمان |

### قانون حریم خصوصی (مهم)

`data` فقط **فراداده‌ی عملیاتی** حمل می‌کند. این موارد **هرگز** در payload
قرار نمی‌گیرند:

- متن پیام کاربر یا پاسخ بات (فقط طول متن، نه خود متن)
- آرگومان‌های ابزار و خروجی ابزار
- محتوای پیوست‌ها

دلیل: endpoint وب‌هوک یک سرور HTTP ثالث است؛ هر چه در `data` بگذارید عملاً با
او به اشتراک گذاشته‌اید. این قانون با «ساختار» تضمین شده نه با «انضباط»:
سازنده‌های رویداد در `src/webhooks/events.ts` تنها جایی هستند که envelope
ساخته می‌شود و فیلدهایشان از قبل محدود به فراداده است. تست
`tests/webhooks.test.ts` هم با یک متن canary بررسی می‌کند که هیچ محتوایی
نشت نکرده باشد.

## امضا و تأیید در سمت گیرنده

هر درخواست این هدر را دارد:

```
X-Bobi-Signature-256: <hex HMAC-SHA256 از بدنه‌ی دقیقِ POST>
```

کلید، همان `BOBI_WEBHOOK_SECRET` است. **تأیید امضا وظیفه‌ی گیرنده است** و باید
با مقایسه‌ی زمان‌ثابت (constant-time) انجام شود تا نشت زمانی رخ ندهد. نمونه‌ی
مرجع (Node.js):

```js
import { createHmac, timingSafeEqual } from "node:crypto";

function verify(secret, body /* رشته‌ی دقیق بدنه */, received /* مقدار هدر */) {
  const expected = Buffer.from(
    createHmac("sha256", secret).update(body, "utf8").digest("hex"),
    "utf8",
  );
  const actual = Buffer.from(received, "utf8");
  return expected.length === actual.length && timingSafeEqual(expected, actual);
}
// در هندلر: بدنه‌ی خام (string) را نگه دارید، JSON.parse را روی کپی انجام دهید،
// چون امضا روی بایت‌های دقیقِ ارسال‌شده حساب شده است.
```

نکته: امضا «اصالت فرستنده» را ثابت می‌کند، نه «تازه‌بودن» رویداد را. اگر
replay برایتان مهم است، فیلد `at` را بررسی کنید و رویدادهای قدیمی‌تر از یک
آستانه (مثلاً ۵ دقیقه) را رد کنید.

## قابلیت اطمینان

- صف درون‌حافظه‌ای با سقف ۱۰۰ رویداد؛ وقتی پر شود **قدیمی‌ترین رویدادِ در
  انتظار** حذف می‌شود (رویدادی که همین حالا در حال ارسال است هرگز قربانی
  نمی‌شود)، شمارنده‌ی `droppedCount` و یک لاگ هشدار ثبت می‌شود.
- هر رویداد حداکثر ۳ بار تلاش می‌شود با backoff نمایی (۱ ثانیه، ۲ ثانیه).
- هر ارسال، timeout جداگانه‌ی ۱۰ ثانیه‌ای دارد؛ endpoint کند نمی‌تواند worker
  را برای همیشه نگه دارد.
- **خرابی ارسال هرگز turn ایجنت را خراب نمی‌کند**: enqueue مسدود نمی‌شود و
  throw نمی‌کند، و خطاها فقط لاگ می‌شوند.

## امنیت / سطح حمله (SECURITY)

1. **SSRF**: مقصدها را فقط مالک بات پیکربندی می‌کند (همان سطحِ `.env` — یک
   سطح پیکربندی مالک-اختصاصی، نه ورودی کاربر). با این حال هر URL اعتبارسنجی
   می‌شود: فقط `http:`/`https:` پذیرفته است و URL دارای userinfo
   (`user:pass@host`) **رد** می‌شود تا هیچ credentialای در URL — و در نتیجه
   در لاگ‌ها یا روی سیم — قرار نگیرد. توجه: چون مقصد مالک-پیکربندی است، این
   اعتبارسنجی برای گرفتن اشتباه تایپی/کپی‌پیست است نه بی‌اعتمادی به مالک.
2. **کلید**: `BOBI_WEBHOOK_SECRET` هرگز لاگ نمی‌شود و در هیچ فایلی نوشته
   نمی‌شود؛ فقط به‌عنوان ماده‌ی کلید HMAC مصرف می‌شود. آن را مثل هر توکن
   دیگری بچرخانید اگر لو رفت.
3. **جعل رویداد**: بدون کلید نمی‌توان امضای معتبر ساخت؛ گیرنده باید امضا را
   با مقایسه‌ی زمان‌ثابت بررسی کند (نمونه بالا). هدر امضا به‌تنهایی و بدون
   تأیید، هیچ ارزشی ندارد.
4. **نشت داده**: قانون حریم خصوصی بالا — payload فقط فراداده است. با این
   حال خودِ فراداده (زمان‌بندی turnها، نام ابزارهای صدا زده‌شده، تعداد
   توکن‌ها) یک نشت جزئیِ الگوی استفاده است؛ endpoint را متعلق به خودتان
   بدانید.
5. **DoS داخلی**: صف محدود (۱۰۰)، timeout ارسال (۱۰s)، و worker تک‌رشته‌ایِ
   غیرمسدودکننده یعنی یک endpoint مرده نمی‌تواند حافظه را باد کند یا turn
   کاربر را معطل کند. تایمرهای داخلی `unref` هستند تا وب‌هوکِ در حال
   تلاش، پروسه را بعد از shutdown زنده نگه ندارد.
6. **حمله‌ی انعکاسی (replay)**: امضا تازگی را تضمین نمی‌کند — گیرنده باید
   `at` را کنترل کند (بخش بالا).

## سیم‌کشی در موتور

نقاط انتشار در `src/conversation/engine.ts` کاملاً additive هستند:

- `runOnce`: قبل از حلقه `agent:start` و در `finally` (موفق یا ناموفق)
  `agent:end` ارسال می‌شود.
- `runAgent`: wrapper دور `onStep` حلقه، بعد از هر `step` از نوع `tool`
  رویداد `tool:end` می‌فرستد. وقتی وب‌هوک فعال باشد این wrapper حتی بدون
  progress sink هم نصب می‌شود تا هیچ `tool:end`ای جا نماند.

همه‌چیز پشت `webhooksEnabled()` است — یک boolean کش‌شده؛ وقتی وب‌هوک
پیکربندی نشده، هزینه‌ی hot path عملاً صفر است و رفتار قبلی بایت‌به‌بایت
حفظ می‌شود.

## تست‌ها

`tests/webhooks.test.ts` (۲۷ تست):

- بردارهای ثابت HMAC (از جمله case 1 از RFC 4231) — مستقل از پیاده‌سازی
  محاسبه شده‌اند.
- URL بدون secret → غیرفعال؛ userinfo و scheme غیر-http → رد.
- صف: drop-oldest با شمارنده، retry با backoff نمایی، تحمل خطای کامل.
- حریم خصوصی: payload هیچ متن پیامی ندارد (تست canary).
- موتور: با وب‌هوک فعال `agent:start`/`agent:end`/`tool:end` ارسال می‌شود و
  امضا درست است؛ با وب‌هوک غیرفعال هیچ‌چیز ارسال نمی‌شود.
