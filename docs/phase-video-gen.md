# فاز B6 — ابزار ساخت ویدیو (generate_video)

ابزار `generate_video` از روی توصیف متنی، یک ویدیوی کوتاه می‌سازد و آن را به کاربر تحویل می‌دهد. دقیقاً همان الگوی `generate_image` (فاز B4) را دنبال می‌کند: فقط وقتی ثبت می‌شود که endpoint پیکربندی شده باشد، ورودی اعتبارسنجی می‌شود، بایت‌ها فقط از مسیر `extractMedia` خارج می‌شوند و `data` امن برای مدل می‌ماند.

## راه‌اندازی

`config.ts` متعلق به بستهٔ کاری دیگری است و نباید دست بخورد؛ بنابراین این ابزار کلیدهای خودش را مستقیم از محیط می‌خواند (`videoGenDepsFromEnv` در `src/tools/video_gen.ts`):

| متغیر محیطی | نقش |
|---|---|
| `BOBI_VIDEO_BASE_URL` (یا `SOL_VIDEO_BASE_URL`) | ریشهٔ endpoint سرویس ویدیوسازی (مثلاً `https://queue.fal.run`). **خالی باشد = ابزار اصلاً ثبت نمی‌شود** و مدل از وجودش باخبر نمی‌شود (همان الگوی `web_search` و `generate_image`). |
| `BOBI_VIDEO_API_KEY` (یا `SOL_VIDEO_API_KEY`) | کلید سرویس؛ اختیاری. فقط در هدر `Authorization` به همان endpoint ارسال می‌شود. |
| `BOBI_VIDEO_MODEL` (یا `SOL_VIDEO_MODEL`) | مدل؛ اختیاری. خالی باشد از بدنهٔ درخواست حذف می‌شود (سرویس‌ها مدل‌های متفاوتی دارند). |

سیم‌کشی در `src/index.ts` (به‌عهدهٔ هماهنگ‌کننده) آینهٔ `generate_image` است:

```ts
const videoEnv = videoGenDepsFromEnv();
if (videoGenConfigured(videoEnv.baseUrl)) {
  extraTools.push(createVideoGenTool(videoEnv) as Tool<unknown, unknown>);
}
```

## ورودی و خروجی

- `prompt` (الزامی): ۱ تا ۱۰۰۰ کاراکتر، فارسی‌دوست (متن UTF-8 بدون هیچ محدودیت زبانی). بیشتر از ۱۰۰۰ در اعتبارسنجی رد می‌شود و هیچ درخواستی ارسال نمی‌شود.
- `size` (اختیاری): `1280x720` (پیش‌فرض) یا `720x1280`.
- `duration_seconds` (اختیاری): عدد صحیح ۱ تا ۳۰؛ پیش‌فرض ۵.
- قرارداد provider (ناهمزمان، مستند در سر فایل):
  - ثبت کار: `POST {baseUrl}/videos/jobs` با `{model?, prompt, n:1, size, duration_seconds}` → `{id}` (نام‌های جایگزین `job_id` و `request_id` هم پذیرفته می‌شوند).
  - نظرسنجی وضعیت: `GET {baseUrl}/videos/jobs/{id}` → `{status, video?}`؛ وضعیت‌های پایانی موفق `succeeded/completed/complete/done` و وضعیت‌های پایانی ناموفق `failed/error/cancelled/canceled`؛ بقیه یعنی «ادامه بده».
  - بار ویدیو: `{video: {b64: "..."}}` (یا `video_b64`) یعنی base64 مستقیم؛ `{video: {url: "..."}}` (یا `video_url`) یعنی دانلود از URL داده‌شده.
- `data` (نتیجهٔ امن برای مدل): فقط `{ok, prompt, size, durationSeconds}` — **هیچ بایت base64ای در آن نیست**.
- بایت‌های ویدیو از مسیر `extractMedia` خارج می‌شوند و لایهٔ بات آن‌ها را برای کاربر می‌فرستد؛ هرگز وارد کانتکست مدل نمی‌شوند.

## محدودیت‌ها

- هر فراخوانی دقیقاً **یک** ویدیو (`n:1`).
- مهلت سخت هر کار **۱۰ دقیقه** (`VIDEO_JOB_TIMEOUT_MS`) به‌علاوهٔ سقف **۱۲۰ تلاش** نظرسنجی (`MAX_POLL_ATTEMPTS`)؛ هرکدام زودتر برسد، اجرا با خطای timeout تمام می‌شود. فاصلهٔ نظرسنجی‌ها ۵ ثانیه و مهلت هر درخواست تکی ۳۰ ثانیه است.
- ابزار `timeoutMs` خودش را روی ۱۱ دقیقه اعلام می‌کند تا اجراکننده، حلقهٔ نظرسنجی را با پیش‌فرض ۱۰ ثانیه‌ای نکشد.
- بودجهٔ حجم: ویدیوی بزرگ‌تر از سقف پاسخ ترنسپورت پین‌شده (۸ مگابایت، `MAX_RESPONSE_BYTES`) مردود است (`MAX_VIDEO_BYTES`) — هم برای base64 درون‌خطی، هم برای دانلود.
- خطای 429 به `overloaded` نگاشت می‌شود تا حلقهٔ عامل عقب‌نشینی کند، نه این‌که سرویس را بکوبد.
- نکتهٔ تحویل: تایپ `ContentPart` هنوز گونهٔ `video` ندارد، پس کلیپ به‌صورت `{type: "document", mediaType: "video/mp4"}` (یا webm/mov بر اساس پسوند امن‌شدهٔ URL) با نام `bobi.mp4` تحویل داده می‌شود و لایهٔ بات آن را از همان مسیر مدیای بقیهٔ ابزارها می‌فرستد. افزودن گونهٔ بومی `video` به `src/bot/media.ts` (مال بستهٔ دیگری است) کارِ پیگیریِ آینده است تا تلگرام آن را به‌صورت ویدیو نمایش دهد.

## مدل امنیتی / سطح حمله

- `prompt` دادهٔ کاربر/مدل است و **فقط** به endpointای می‌رود که مالک در پیکربندی مشخص کرده؛ هیچ بخشی از ورودی نمی‌تواند هاست، مسیر یا اسکیم را عوض کند.
- همهٔ HTTP (ثبت کار، نظرسنجی وضعیت، دانلود) از `resolveTarget` + `pinnedFetch` می‌گذرد (همان ترنسپورت پین‌شدهٔ آداپترها): رزولوشن DNS و رده‌بندی همهٔ آدرس‌ها پیش از باز شدن سوکت، عدم دنبال‌کردن ریدایرکت، و بستن اتصال به آدرس‌های تأییدشده. هدف‌های داخلی/خصوصی مردودند (استثنای local در این‌جا فعال نیست).
- **نکتهٔ مهم سطح حمله — URL دانلود خروجی provider است، نه ورودی مالک.** اگر provider به‌جای base64 یک `url` برگرداند، آن URL هم پیش از هر دانلودی از `resolveTarget` می‌گذرد: اسکیم غیر HTTP/HTTPS، آدرس داخلی/خصوصی و متادیتا رد می‌شود. پس provider نمی‌تواند دانلود را به سمت شبکهٔ داخلی بچرخاند (SSRF).
- کلید API هرگز در پیام خطا یا لاگ تکرار نمی‌شود؛ بدنهٔ خام پاسخ سرویس هم در خطاها بازتاب داده نمی‌شود. (اجراکننده پیام‌های `invalid_result` را هم به‌صورت پیش‌فرض پاک‌سازی می‌کند.)
- بایت‌های تولیدشده خروجیِ provider هستند و «داده» تلقی می‌شوند: مدل آن‌ها را نمی‌بیند و فقط کاربر نهایی ویدیو را دریافت می‌کند؛ بایت‌ها هرگز اجرا نمی‌شوند.
- حلقهٔ نظرسنجی با دو سقف سخت (زمان و تعداد تلاش) محدود است و با `ctx.signal` لغو می‌شود؛ provider نمی‌تواند ابزار را برای همیشه مشغول نگه دارد.
- پسوند فایل از URL با عبارت منظم امن استخراج می‌شود (فقط `mp4/webm/mov`، بقیه → `mp4`) تا ورودی provider نتواند نام فایل دلخواه تزریق کند.

## مجوز

مدل مجوزی دقیقاً آینهٔ `generate_image`: `permission: { requires: ["tools:generate_video"] }` بدون پرچم `ownerOnly`؛ ابزار در تول‌ست `media` ثبت می‌شود.
